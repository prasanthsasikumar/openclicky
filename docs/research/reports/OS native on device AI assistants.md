# Nobody ships the OS-model-first desktop assistant yet

Research date: 2026-10-27. Synthesised from five research notes in `docs/research/research_notes/OS native on device AI assistants/` (macOS Foundation Models, Windows AI Foundry/Phi Silica, Linux local models, hybrid routing in shipped assistants, accessibility and HCI prior art).

No shipped product combines the three things OpenClicky is about to combine: the OS vendor's own on-device language model as the first rung, a general desktop voice assistant that rewrites, classifies, acts and answers about the screen, and a cloud fallback. Each pair exists. Apple's September 2025 showcase names ~21 apps on the Foundation Models framework, all doing small structured tasks and none advertising a cloud fallback ([Apple Newsroom](https://www.apple.com/newsroom/2025/09/apples-foundation-models-framework-unlocks-new-intelligent-app-experiences/)); Microsoft's own Notepad, Click to Do, Narrator and Fluid Dictation run on Phi Silica on Copilot+ PCs with a cloud path behind a paywall or an explicit user action, but **no third-party app was found that publicly uses the Phi Silica `LanguageModel` API**, a gate that only lifted today when Windows App SDK 2.6.4 dropped the Limited Access Feature token ([release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable)); Linux has no OS model API at all, only Ollama and llama.cpp as de facto services. Across ~30 shipped assistants and dictation tools, **not one routes between local and cloud by confidence or difficulty**: the rules are a manual picker, a fixed per-feature split, an availability check (Google's `PREFER_ON_DEVICE`, Microsoft's readiness cascade), or Home Assistant's "known command matched locally, else LLM" ([HA 2024.12](https://www.home-assistant.io/blog/2024/12/04/release-202412/)). The accessibility literature is unanimous that small on-device models are trusted to describe, read, clean up and point, never to act unsupervised, and every peer-reviewed LLM assistant evaluated with blind or older users ran a cloud frontier model, so the intersection is an open research slot as well as an open product slot. The practical envelope for the first rung is the same on all three platforms: a ~3B model, a ~4k-token budget, text in and text out, schema-constrained output, availability that depends on hardware, language and OS settings the user did not choose, and a silent fallback that must exist before the feature does.

## The pieces exist separately; the triple does not

The closest precedents sort into four families, and the pattern each has converged on is instructive because none of them had to solve OpenClicky's whole problem. Apple's showcase apps (OmniFocus 4.8 generating sub-tasks, Stuff parsing dates and tags while you type, Agenda answering questions about your notes, Signeasy summarising a document) chose tasks that fit guided generation and a 4k session, and Apple frames the framework as free, offline and private rather than as one tier of a hybrid ([Apple Newsroom](https://www.apple.com/newsroom/2025/09/apples-foundation-models-framework-unlocks-new-intelligent-app-experiences/); [Omni Group](https://www.omnigroup.com/blog/ready-for-os-26)). The fallback story on macOS is carried by libraries, not apps: AnyLanguageModel lets you swap the `import` and keep the API across Apple's model, MLX, llama.cpp, Ollama, OpenAI, Anthropic and Gemini, and explicitly positions Apple's model as "a system-level fallback in hybrid app designs" ([Hugging Face](https://huggingface.co/blog/anylanguagemodel)); OpenFoundationModels reimplements the API with cloud backends behind build traits ([Swift Forums](https://forums.swift.org/t/openfoundationmodels-apple-compatible-foundation-models-api-with-multi-provider-support/82168)). From macOS 27 Apple itself makes the backend a session parameter through a `LanguageModel` protocol with `PrivateCloudComputeLanguageModel` and Anthropic and Google packages ([WWDC26 241](https://developer.apple.com/videos/play/wwdc2026/241/)). Osaurus, a macOS local-model server, is the only product found that automatically switches away from Apple's model when Apple Intelligence is off, downloading, or a request stalls, and it falls to an MLX model rather than to the cloud ([Osaurus docs](https://docs.osaurus.ai/models/apple-intelligence)).

The second family is the OS vendors' own accessibility and writing features, and here the two-tier shape is identical everywhere. Google TalkBack describes images on-device with Gemini Nano, and a richer description from server-side Gemini 1.5 Flash is a separate menu action the user invokes ([Android Developers Blog](https://android-developers.googleblog.com/2024/09/talkback-uses-gemini-nano-to-increase-low-vision-accessibility.html)). Microsoft Narrator gives instant on-device image descriptions on Copilot+ PCs and, since the January 2026 Insider build, a Copilot cloud description on every other Windows 11 device, again only after the user asks ([Windows Insider blog](https://blogs.windows.com/windows-insider/2026/01/09/announcing-windows-11-insider-preview-build-26220-7535-dev-beta-channels)). Notepad is the cleanest first-party hybrid: local model on Copilot+ PCs, otherwise an Azure service metered by **60 Microsoft 365 AI credits a month**, which means Microsoft does not give non-Copilot+ users a free cloud path and a third-party app cannot piggyback on one ([Microsoft Support](https://support.microsoft.com/windows/enhance-your-writing-with-ai-in-notepad-4088b954-c97b-46dc-813f-959be01746d5)). Fluid Dictation cleans up grammar and fillers on "on-device small language models" and is disabled in password and PIN fields ([Microsoft Support](https://support.microsoft.com/ja-jp/Accessibility/windows/voice-access/fluid-dictation)). Apple's own accessibility ML remains task-specific (Screen Recognition since iOS 14, Personal Voice, Live Recognition on visionOS); no Apple source ties VoiceOver or Accessibility Reader to the Apple Intelligence model ([Apple Newsroom 2025-05-13](https://www.apple.com/newsroom/2025/05/apple-unveils-powerful-accessibility-features-coming-later-this-year/)).

The third family, dictation tools, is the one OpenClicky already belongs to, and it solved the local-tier problem by shrinking the task rather than by escalating. Superwhisper's S1-mini is a **0.6B Qwen3 fine-tune (484 MB)** that is "not a chat model and won't follow general instructions" ([Superwhisper](https://superwhisper.com/blog/s1)); Spokenly Cleanup 1 "keeps your wording" and passes text through unchanged above ~1,600 English words or outside seven languages ([Spokenly docs](https://spokenly.app/docs/macos/local-model-cleanup)); OpenWhispr pastes raw dictation when cleanup cannot run ([OpenWhispr docs](https://docs.openwhispr.com/help/dictation/cleanup.md)); Handy exposes Apple Intelligence as a post-processing provider but simply fails offline ([Handy docs](https://handy.computer/docs/post-processing)). The "fallback" in this market is deterministic pass-through on length, language or timeout, not a cloud call. The fourth family is the Clicky lineage itself: three unmerged PRs on farzaa/clicky add LM Studio routing by model-name string match (#28), on-device Parakeet and Supertonic (#68), and an MLX Llama-3.2-3B "Local Mode" with a manual picker that disables screenshots and pointing entirely, whose author lists an "auto-routing brain" as the thing to build next ([farzaa/clicky #115](https://github.com/farzaa/clicky/pull/115)). On Linux, Newelle, Alpaca and Bavarder are GTK4 provider pickers in which Ollama is one option, with no automatic routing described ([Newelle](https://github.com/qwersyk/Newelle)); OrcaVision is the sole screen-reader pairing, sending screenshots to a vision model that may be a local Ollama server ([OrcaVision](https://github.com/whoknowsla/orcavision)).

| Precedent | On-device model | Cloud tier | Routing rule | Covers OpenClicky's tasks? |
|---|---|---|---|---|
| Apple showcase apps (OmniFocus, Stuff, Agenda) | Apple FM, ~3B | none advertised | n/a | classify, extract, short summarise |
| Notepad / Click to Do / Narrator | Phi Silica | M365 credits or Copilot, user-invoked | hardware tier | rewrite, summarise, describe |
| TalkBack | Gemini Nano | Gemini Flash on "Describe Image" | user escalation | describe |
| Home Assistant Assist | closed intent grammar | any LLM | strict match else LLM | quick actions |
| Superwhisper / Spokenly | 0.6B cleanup models | manual picker | length/language pass-through | dictation clean-up |
| Clicky PR #115 | MLX Llama-3.2-3B | Claude | manual picker, no screen in local | chat without screen |
| Osaurus | Apple FM | MLX model | unavailable or stalled | generic chat |

## Each OS offers roughly the same 3B model behind a different gate

The three platforms converge on capability and diverge on who is allowed to use it. Apple's on-device model is **~3B parameters, 2-bit quantised, text-only on macOS 26**, with a **4,096-token session limit that counts instructions, prior turns, tool schemas, tool output and generated text** ([WWDC25 286](https://developer.apple.com/videos/play/wwdc2025/286/); [Apple Developer Forums 806542](https://origin-devforums.apple.com/forums/thread/806542?answerId=865200022)). It runs on any M-series Mac with Apple Intelligence enabled, but only when the Siri language, not the system language, is one of 16 supported ones, so Catalan, Polish, Finnish, Czech, Greek and Hungarian users get `isSupported == false` even on a new Mac ([Apple Developer Forums 805378](https://developer.apple.com/forums/thread/805378); [Apple Support](https://support.apple.com/en-us/121115)). It is un-rate-limited in the foreground or on power, but Apple engineers confirm throttling when the device is on battery and the process is in the background, with Safari extensions counting as background, and streaming hits the limit sooner than `respond` ([Apple Developer Forums 789788](https://developer.apple.com/forums/thread/789788)). Guardrails fire on innocuous text, prompt language affects sensitivity, and `guardrailViolation` and `unsupportedLanguageOrLocale` are non-recoverable, while `exceededContextWindowSize` is recoverable by rebuilding the session ([drobinin.com](https://drobinin.com/consulting/foundation-models-apple-intelligence/putting-apple-foundation-models-in-a-real-app/)). An August 2026 audit found the model **confabulates on 69% of false-premise questions and refuses 18% of benign prompts**, with self-reported confidence no better than chance (AUROC 0.47) ([arXiv 2608.23663](https://arxiv.org/abs/2608.23663)). What it does well is schema-pinned work: constrained decoding through `@Generable` and `@Guide` "fundamentally guarantees structural correctness" and "tends to improve model accuracy", and tool calling built on it never produces an invalid tool name, though Apple's own rule of thumb is three to four tools per session ([WWDC25 301](https://developer.apple.com/videos/play/wwdc2025/301/); [Code-along Q&A](https://gist.github.com/stinger/81891077161002819c0ec233f73edc74)). macOS 27 changes the ceiling rather than the floor: a rebuilt model with image attachments, `contextSize` reporting 8,192 on newer hardware, system `OCRTool` and Spotlight tools for local RAG, an Evaluations framework, and `PrivateCloudComputeLanguageModel` with a **32k context, no API keys and no cloud cost for apps under 2M first-time downloads**, behind an entitlement and a daily per-user quota ([WWDC26 241](https://developer.apple.com/videos/play/wwdc2026/241/); [WWDC26 319](https://developer.apple.com/videos/play/wwdc2026/319)). LoRA adapters are impractical for a small team: ~160 MB per adapter, one per model version, and the 26.0 toolkit is "not compatible with OS 27 and later" ([Apple adapter toolkit](https://developer.apple.com/apple-intelligence/foundation-models-adapter/)).

Windows offers a near-identical model with a far narrower door, and the door is moving. Phi Silica is a **~3.3B, 4-bit derivative of Phi-3.5-mini with a 4k context**, eight launch languages, **230 ms time to first token and up to 20 tokens/s** on Snapdragon X NPUs, the only official throughput numbers Microsoft has published ([Windows blog 2024-12-06](https://blogs.windows.com/windowsexperience/2024/12/06/phi-silica-small-but-mighty-on-device-slm/)). It is preinstalled only on Copilot+ PCs (40+ TOPS NPU, 16 GB RAM); CPU execution is "Not supported", and the GPU path needs an RTX 30-series or RX 9060 with 6 GB VRAM plus an Insider Experimental build, Developer Mode, an experimental SDK and a vendor beta driver, so an ordinary x64 laptop with integrated graphics returns `NotSupportedOnCurrentSystem` ([What are Windows AI APIs?](https://learn.microsoft.com/en-us/windows/ai/apis/); [Phi Silica](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica)). The API surface is richer than Apple's in one way and poorer in another: it has `TextRewriter` with tone, `TextSummarizer`, text-to-table, embeddings, configurable content moderation and `GenerateStructuredJsonResponseAsync` constrained to a caller-supplied JSON schema (stable since 2.3.1), but **no tool or function calling** ([LanguageModel class](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.ai.text.languagemodel)). Since October 2026 free-text outputs carry an invisible four-code-point Unicode watermark (`U+200B U+034F U+2060 U+200B`) that Microsoft warns "can cause issues" when parsing JSON or Markdown; the structured JSON API is not on the watermarked list ([Watermarking](https://learn.microsoft.com/en-us/windows/ai/apis/text-watermarking)). Using it from WPF is possible on paper (the get-started page has a WPF tab targeting `net8.0-windows10.0.22621.0`) but the AI APIs require package identity and the `systemAIModels` capability, so a plain xcopy exe fails with `UnauthorizedAccessException` and a Microsoft moderator's advice in February 2026 was to use a packaged WinUI 3 app instead of plain WPF ([Get started](https://learn.microsoft.com/en-us/windows/ai/apis/get-started); [Troubleshooting](https://learn.microsoft.com/en-us/windows/ai/apis/troubleshooting); [Microsoft Q&A](https://learn.microsoft.com/en-au/answers/questions/5761829/is-it-possible-to-create-a-desktop-application-tha)). And the model itself is being retired: **Aion Instruct reaches Insiders in November 2026 and retail in January 2027, "at which point Phi Silica will be removed"**; the `LanguageModel` API stays, LoRAs must be retrained, and Microsoft describes Aion as built "for everyday text tasks like summarization, rewriting, intent detection, and accessibility" with CPU inference in Edge, though it has not said the Windows App SDK path will reach CPU-only PCs ([Phi Silica](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica); [Build 2026](https://blogs.windows.com/windowsdeveloper/2026/06/02/build-2026-furthering-windows-as-the-trusted-platform-for-development/)). The rung Microsoft documents below Phi Silica is Foundry Local: GA since 2026-04-09, an in-process ONNX Runtime stack that adds ~20 MB to the app, runs on CPU, GPU or NPU on Windows 10 and later, macOS and Linux, needs no Azure account, no token and no NPU, works in "a WPF app, or any other .NET host", and downloads multi-gigabyte models such as `phi-4-mini` on first use ([Foundry Local GA](https://devblogs.microsoft.com/foundry/foundry-local-ga/); [Foundry Local on Windows](https://learn.microsoft.com/en-us/windows/ai/foundry-local/get-started)). Its Windows quickstart requires .NET 9 and whether the WinML package supports a net8.0 TFM was not verified.

Linux has no first-party rung and none is coming within a planning horizon. Canonical's inference snaps (public beta 2025-10-23) package a model with a hardware-matched OpenVINO runtime and "local and standard inference endpoints", but they are per-model developer packaging with an undocumented endpoint contract, not a desktop API ([Canonical](https://canonical.com/blog/canonical-releases-inference-snaps); [canonical/inference-snaps](https://github.com/canonical/inference-snaps)). GNOME and KDE spent 2025–2026 on contribution policies; KDE's "Kadai" is a conference proposal, Alpaka is an unreleased Ollama client ([HowToGeek](https://www.howtogeek.com/kde-is-fighting-over-whether-ai-belongs-in-linux-heres-whats-at-stake/); [apps.kde.org](https://apps.kde.org/alpaka/)). The de facto service is Ollama on `http://localhost:11434` with an OpenAI-compatible `/v1` surface, JSON-schema `format` enforcement and tool calling ([Ollama API](https://docs.ollama.com/api); [structured outputs](https://docs.ollama.com/capabilities/structured-outputs)), and llama.cpp's `llama-server` (default `127.0.0.1:9931`, `GET /health`, `-hf` auto-download, `json_schema` and `grammar` sampling for any GGUF) when the app wants to own the runtime ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). Throughput on the machines older adults own is the limit: bandwidth-derived estimates put a 3–4B Q4 model at **15–20 tokens/s on dual-channel DDR4 and 7–10 tokens/s on single-channel DDR4**, so a 60-token rewrite takes roughly six to nine seconds after prompt processing on an 8 GB laptop ([PromptQuorum](https://www.promptquorum.com/local-llms/best-cpu-only-llm)). Firefox's floor for its 360M-parameter link-preview summariser is >3 GB available RAM, a useful datum for what "works on old hardware" means ([Mozilla Connect](https://connect.mozilla.org/t5/discussions/try-link-previews-in-firefox-142-see-what-s-behind-a-link-before/m-p/103496)).

| | macOS 26 (27) | Windows 11 | Linux |
|---|---|---|---|
| Model | Apple FM ~3B, 2-bit | Phi Silica ~3.3B, 4-bit → Aion Instruct Jan 2027 | none; Ollama / llama-server (Qwen3-4B, Phi-4-mini, Llama 3.2 3B) |
| Context | 4,096 shared in/out (8,192 on 27 newer HW) | 4k | runtime default 4,096 (Ollama) |

| Tool calling | yes, 3–4 tools | no | yes (runtime-level) |
| Images | 27 only | no (separate NPU-only image APIs) | model-dependent |
| App packaging | none | package identity + `systemAIModels` + SDK 2.6.4 | none |

| Fallback below OS model | MLX / llama.cpp | Foundry Local (any PC) | bundle llama-server |

## Shipped routers decide by availability and task, never by confidence

Every system that has reached users decides between tiers with signals the app controls, and the research literature explains why that is the right call at 3B scale. Google's hybrid API is the only vendor surface that is literally "prefer on-device, else cloud", and its "else" is defined as cannot run: model unavailable, download in progress, unsupported modality, multi-turn chat, function calling, or input over **9,216 tokens**; Google's own April 2026 blog calls it a "simple rule-based routing approach as an initial solution" and warns that falling back to the cloud "may have legal or functional consequences" that require consent ([Firebase hybrid](https://firebase.google.com/docs/ai-logic/hybrid-on-device-inference); [Android Developers Blog](https://android-developers.googleblog.com/2026/04/Hybrid-inference-and-new-AI-models-are-coming-to-Android.html); [Chrome Firebase page](https://developer.chrome.com/docs/ai/firebase-ai-logic)). Microsoft's guidance (updated 2026-10-14) is the most directly actionable: probe local readiness first, ask consent before a multi-GB download, call the cloud only when policy allows, keep both paths behind one abstraction, log which path ran, and **classify the task before picking a model** using "the feature or UI entry point, input length, or a lightweight local classification step" rather than "attempting local inference first and discarding a low-quality result" ([Choose between cloud and local](https://learn.microsoft.com/en-us/windows/ai/cloud-ai)). Its three-tier sample is `LanguageModel.GetReadyState()` → `foundryClient.IsModelAvailableAsync("phi-4-mini")` → Azure OpenAI ([Choose your Windows AI solution](https://learn.microsoft.com/en-us/windows/ai/windows-ai-comparison)), and the AI Dev Gallery already wraps Phi Silica, Foundry Local, ONNX GenAI, Ollama and OpenAI behind one `Microsoft.Extensions.AI.IChatClient` ([microsoft/ai-dev-gallery](https://github.com/microsoft/ai-dev-gallery)).

Home Assistant is the strongest precedent for the quick-actions rung specifically. Since 2024.12 its pipeline tries sentence triggers, then strict local intent matching "with exposed entities and exact wording", and only when nothing matches calls the LLM; there is no confidence score, the match is binary ([HA 2024.12](https://www.home-assistant.io/blog/2024/12/04/release-202412/); [default_agent.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/conversation/default_agent.py)). Two years of bug reports map the failure modes an OpenClicky router will meet: a locally matched intent that cannot execute used to fall through to the LLM, which then "invented values" (fixed in October 2026 by not writing the phantom tool call to the chat log) ([PR #186708](https://github.com/home-assistant/core/pull/186708); [HA community](https://community.home-assistant.io/t/my-journey-to-a-reliable-and-enjoyable-locally-hosted-voice-assistant/944860/13)); two intents are deliberately withheld from local handling when the LLM has control because the small tier answers them badly ([default_pipeline.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/assist_pipeline/default_pipeline.py)); follow-up turns stay with whichever tier answered last, by design ([core issue #162768](https://github.com/home-assistant/core/issues/162768)); and intent recognition is warmed up while the user is still speaking to hide cold start ([PR #186711](https://github.com/home-assistant/core/pull/186711)).

The literature confirms that post-hoc confidence from a small model is not a usable signal at this scale. RouteLLM reaches 95% of GPT-4 quality with 26% of calls, and Hybrid LLM cuts GPT-3.5 calls 22% at a 1% quality loss, but those pair 7–13B models with cloud; the one row with a sub-1B small model (FLAN-T5-800M → Llama-2-13B) **loses 10–14 quality points at 40% offload** ([LMSYS](https://lmsys.org/blog/2024-07-01-routellm/); [arXiv 2404.14618](https://arxiv.org/html/2404.14618v1)). Sequence-level confidence is "strongly sub-optimal because of a length bias" ([arXiv 2404.10136](https://arxiv.org/html/2404.10136v1)), and normalised entropy "collapses to near-random discrimination at 1B and below" ([Research Square](https://www.researchsquare.com/article/rs-10911915)), consistent with the AUROC 0.47 measured for Apple's model. Post-hoc deferral also pays the full local latency before escalating. What the web platform guidance recommends instead is capability-based escalation, where a small classifier sorts requests into common (local) and uncommon (server), with a worked example of roughly 80% routine ([web.dev](https://web.dev/learn/ai/platform)), and Arch-Router shows a 1.5B generative router hitting 93% routing accuracy on user-defined policies, small enough to run locally ([arXiv 2506.16655](https://arxiv.org/pdf/2506.16655)).

The practitioner pitfalls are deterministic too, and OpenClicky has already met the first one. Small rewrite models answer the dictation instead of rewriting it: Paraspeech users dictating "which model are you" got "I am Claude" ([Paraspeech board](https://paraspeech.userjot.com/board/p/when-rewriting-transcribed-dictation-thinks-i-m-asking-it-a)), AssemblyAI's docs admit the model "will occasionally answer a question it heard in the audio" ([AssemblyAI](https://www.assemblyai.com/docs/dictation/transcript-rewriting.md)), and the comment in OpenClicky's `AppleModelTakePolisher.swift` records the same behaviour before the `<dictation>` tag framing was added. Handy warns that "small models (under 3B parameters) may ignore prompts" ([Handy docs](https://handy.computer/docs/post-processing)); Khoj skipped offline JSON extraction because the small model could not emit reliable JSON ([Khoj PR #680](https://github.com/khoj-ai/khoj/pull/680)); an unconstrained Gemma 3 4B hit 100% JSON parse but only 87% schema compliance ([AscentCore](https://ascentcore.com/2026/04/01/small-llm-performance-benchmark/)), which is the argument for runtime-enforced schemas everywhere. Always-loaded local models hold memory (S1-mini sits at ~900 MB idle on a 16 GB Mac mini) ([Superwhisper board](https://superwhisper.userjot.com/board/p/let-s1-mini-unload-when-superwhisper-is-idle)); "local" toggles miss code paths (Raycast's Extension API and emoji search still reach its servers, Brave's BYOM skips Search) ([Raycast manual](https://manual.raycast.com/ai/local-models.md)); and cloud-first without a reachability probe produced a 120-second `waitsForConnectivity` hang in upstream Clicky ([farzaa/clicky #115](https://github.com/farzaa/clicky/pull/115)).

## Accessibility research trusts small models to describe and point, not to act

The HCI record sets the trust boundary more clearly than any vendor document. Every peer-reviewed LLM assistant evaluated with blind or older users ran a cloud frontier model, and even those fail often: in the EMNLP 2026 field study of computer-use agents with eight blind screen-reader users across 1,258 commands, **GPT-5 fully succeeded on 52.5% of tasks**, other models on 38–49%, with failures in grounding, planning, constraint tracking and termination; participants wanted to be told "where I am, what options are available, and what I should do next", wanted confirmation before hard-to-undo actions and a reliable "done" signal, and some withdrew banking and password tasks ([arXiv 2609.00524](https://arxiv.org/abs/2609.00524); [Nielsen](https://jakobnielsenphd.substack.com/p/ux-roundup-20260925)). Guidance beats automation for older adults on the evidence available: GuideMe (CHI 2026) clarifies intent with counter-questions and then hollows out the target on an overlay, cutting incorrect taps from 2.94 to **0.11** against an LLM-search baseline and matching an in-person tutor on most workload measures, at the cost of a longer asking phase ([ACM DL](https://dl.acm.org/doi/10.1145/3772318.3791448); [review](https://a11y-paradise.onrender.com/reviews/69e7deb19cd3fefd1e4d88bd)). Older adults' instructions are indirect, ambiguous and under-specified, and mainstream GUI agents degrade substantially on them ([ElderBench, arXiv 2609.04850](https://arxiv.org/abs/2609.04850)); LLM rephrasing of their problem descriptions raised automated solution accuracy from 35% to 69% ([arXiv 2601.10018](https://arxiv.org/abs/2601.10018)), which is a rewrite task, exactly the class a 3B model handles.

Trust calibration is the second finding that matters for a vulnerable population. Over a two-week diary with 20 blind and low-vision users, an MLLM visual assistant was wrong on 22.2% of answers yet rated 3.76/5 trustworthy ([arXiv 2602.13469](https://arxiv.org/abs/2602.13469)); blind users assume captions are correct and self-blame when AI fails ([arXiv 2604.00187](https://arxiv.org/abs/2604.00187)). The one uncertainty signal with experimental support is content, not a number: surfacing where multiple model answers disagree improved 15 BLV participants' detection of unreliable claims about 4.9-fold and lowered perceived reliability from 5.78 to 3.93 out of 7 ([ASSETS 2025, arXiv 2507.15692](https://arxiv.org/abs/2507.15692v1)). For cognitive impairment, protective constraints that suit severe impairment restrict autonomy at mild impairment, so safeguards must be adjustable ([arXiv 2608.17175](https://arxiv.org/abs/2608.17175)). NV Access's experience is the cautionary tale on the engineering side: NVDA merged local image captioning with a ViT-GPT2 ONNX model in September 2025 and reverted it in January 2026 because captions were poor, numpy and onnxruntime bloated startup, and ONNX failed under ARM64 emulation ([nvaccess/nvda PR 18475](https://github.com/nvaccess/nvda/pull/18475)); a vendor-managed OS model removes exactly that packaging burden, which is the strongest practical argument for using it where it exists. The intersection of OS-vendor on-device model, desktop guidance and older or low-vision users has no published study and no shipped product; a 10–20 participant, two-to-three-week in-the-wild study is the field's normal sample size and would be first.

## Implications and recommendations for OpenClicky

The evidence supports one routing contract shared across the three clients and three different implementations of the local rung. The contract: the local tier gets only transformations with a checkable output shape and a small input, chosen by entry point and input length before any model runs; availability is probed at use, not at install; the fallback triggers are availability, hard error classes and deterministic caps, never a confidence score; and every escalation is visible. Mapped onto the tasks in the question, that gives the following split, which is consistent with Microsoft's complexity guidance, Apple's "not designed for world knowledge" framing and the accessibility trust boundary.

| Task | Local rung | Fallback trigger | Notes |
|---|---|---|---|
| Dictation clean-up | yes (shipped on macOS) | unavailable, guardrail, language, timeout → pass raw text through, then key/account | keep `<dictation>` framing; add a length-ratio sanity check |
| Rewrite / rephrase selected text | yes, up to ~2,500 input tokens | context overflow, guardrail → cloud | schema-pin to a single string; temperature low |
| Summarise | yes for short, extractive summaries | input over budget → cloud, not chunking | 4k shared in/out on all three OS models |
| Intent classification | yes, as an enum | never; a "cloud" bucket in the enum is the escalation | cheapest and most reliable local task |
| Quick actions (open app, volume) | classify locally, dispatch in app code | no match → cloud or ask | mirror Home Assistant: binary match, confirm before hard-to-undo |
| Questions about on-screen text | only extractive ("read me the error") over OCR/AX text that fits | interpretive or long → cloud | 69% false-premise confabulation; never open Q&A locally |
| Teach Me, pointing, agent tasks | no | always cloud | grounding plus planning is where small models fail |

On macOS the first rung already exists in `AppleModelTakePolisher` and should be generalised rather than duplicated. Replace free-text responses with `@Generable` types for every task (a `String` field for rewrite, an `anyOf` enum for intent that includes an explicit `needsCloud` case, a short struct for extractive answers) because constrained decoding is where the model's reliability comes from; keep quick actions as an enum plus app-side dispatch rather than as Apple tools, both to stay within the three-to-four-tool guidance and to share one dispatch path with Windows, which has no tool calling. Prewarm the session when the ⌃⌥ hotkey goes down, the Home Assistant trick, since `prewarm()` saves about 500 ms and shipped apps report one-to-two-second cold starts ([Code-along Q&A](https://gist.github.com/stinger/81891077161002819c0ec233f73edc74)). Treat the background-on-battery throttle as a live risk: OpenClicky is a menu-bar agent whose window is rarely key, Safari extensions already count as background, and the failure surfaces as a misleading guardrail error, so use `respond` rather than streaming for the local rung and test on battery with the HUD hidden ([Apple Developer Forums 789788](https://developer.apple.com/forums/thread/789788)). Map errors deliberately: `exceededContextWindowSize` → straight to cloud (the input will not shrink), `guardrailViolation` and `unsupportedLanguageOrLocale` → cloud silently with no retry, rate limit → cloud with a log line. Check `supportsLocale` per utterance, as the polisher already does, because a user whose Siri language is unsupported gets nothing from the model regardless of hardware. For macOS 27, plan the second rung as `PrivateCloudComputeLanguageModel` (32k context, no key, free under 2M downloads) between the on-device model and the user's own keys, adopt the `LanguageModel` protocol so the rung is a session parameter, and use the system `OCRTool` and image attachments for on-screen questions; skip adapters entirely. For macOS 26 parity, AnyLanguageModel is the lowest-friction way to write one code path across Apple's model and keyed providers.

On Windows the honest recommendation is that Phi Silica cannot be the first rung for today's users, and Foundry Local can. The installed base of older adults' laptops is NPU-less with integrated graphics, which yields `NotSupportedOnCurrentSystem`, and OpenClicky's WPF client ships unpackaged and unsigned, while the AI APIs need package identity plus the `systemAIModels` capability on top of SDK 2.6.4. Build the abstraction now anyway: one `IChatClient`-shaped interface (the AI Dev Gallery's `PhiSilicaClient` and `FoundryLocalChatClientAdapter` are the reference) with the readiness cascade Microsoft documents, so that packaging and signing work, already pending for SignPath, unlocks the OS model without touching the routing. For the OS-model path, use `GenerateStructuredJsonResponseAsync` for intent and extraction because it is schema-constrained and not on the watermark list, and strip the `U+200B U+034F U+2060 U+200B` sequence from any free-text output before parsing; use `TextRewriter` and `TextSummarizer` for the writing tasks since those are the exact first-party skills behind Notepad and Click to Do. Expect to re-test every prompt in January 2027 when Aion Instruct replaces the model under the same API. For the Foundry Local path, gate the multi-gigabyte `phi-4-mini` download behind the same consent and disk-space checks the Linux client already applies to Parakeet, pin a model version, and verify the WinML package against the net8.0 target before committing, since the quickstart requires .NET 9. There is no free Microsoft cloud tier for third parties, so the cloud rung on Windows remains the user's own key or the OpenClicky account.

On Linux the app owns the whole stack, and the design should mirror the existing optional offline engine. Probe in order `GET 127.0.0.1:11434/api/tags` (honouring `OLLAMA_HOST`), `GET 127.0.0.1:9931/health` and `:8080/health` for llama-server, and `GET 127.0.0.1:1234/v1/models` for LM Studio; all speak the OpenAI chat shape, so one client suffices, and every request must carry a JSON schema in `format` or `json_schema` because unconstrained small models miss schema compliance 13% of the time. Offer a bundled option that downloads a ~2–2.5 GB Q4 GGUF (Qwen3-4B or Phi-4-mini for quality, Qwen3-1.7B for 8 GB single-channel machines) and runs `llama-server -hf … --port <ephemeral>` as a helper process with `/health` as the readiness signal, reusing `offline.py`'s download, free-space and idle-unload logic; keep it warm across a session or own the process, since Ollama unloads after five minutes idle and reloading a 2 GB file on an old SSD costs seconds. Set the latency expectation at 7–10 tokens/s on single-channel laptops and use the timeout-with-pass-through rule from Voxtype and OpenWhispr. Treat this rung as "a local model the user or the app installed", not an OS model, in the settings copy; nothing in Canonical's, GNOME's or KDE's roadmaps changes that within a year. For screen-reader users, an Orca 51 user extension is the sanctioned integration point if OpenClicky wants to speak through Orca rather than beside it.

Three cross-platform rules follow from the pitfalls. First, the local tier never sees a screenshot and never answers open questions about the screen; on-screen text reaches it only as extracted OCR or accessibility-tree text that fits the budget, and only for extractive requests, which is both the Clicky #115 capability boundary and the accessibility trust boundary. Second, make the tier audible: a short spoken or HUD cue when an answer came from the cloud makes inconsistent voice attributable and makes data egress a known event, the property TalkBack and Narrator preserve by making cloud an explicit action. Third, exclude secure fields from any local rewrite, as Fluid Dictation does, and keep every state-changing action behind the existing pre-send pause and wrong-click check regardless of which tier classified it.

## Conclusion

The research reframes the question from "which model is good enough" to "which gate is the user behind". On all three platforms the on-device model is the same ~3B, ~4k-token, text-first engine, and the design that works with it is already settled by Apple's showcase apps, Microsoft's inbox features and the dictation market: narrow, schema-pinned transformations, chosen by entry point and length, with deterministic pass-through or escalation. What differs is who gets it. On macOS the gate is the Siri language and the Apple Intelligence toggle; on Windows it is a 40-TOPS NPU plus app packaging, with the model itself swapped out in January 2027; on Linux there is no gate because there is no model, so the app must become the vendor. OpenClicky's three clients therefore need one routing contract and three unrelated first rungs, and the Windows and Linux rungs will be Foundry Local and llama-server for the foreseeable future rather than anything the OS supplies.

The open slot is real and it is the project's own population. No product routes a desktop assistant through an OS model with a cloud fallback, no study has put an on-device model in front of older or blind desktop users, and the one interaction pattern with strong evidence for older adults, clarify-then-point, needs grounding but not planning, which is the single task class where a 3B model is plausibly adequate. Building the first rung as described, instrumenting which tier answered, and running a two-to-three-week field study with 10–20 Singapore participants would produce both a better product and the first paper at that intersection.
