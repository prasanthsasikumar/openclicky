# Hybrid routing in desktop assistants and dictation tools: local small model first, cloud fallback (and the reverse)

Research date: 2026-10-27. Every claim carries the date of its source or the date it was seen. "Shipped" means in a release channel a user can install; "announced/preview" means blog, dev channel, waitlist or open PR only. Three parallel sub-researchers covered (a) dictation and local-LLM desktop apps, (b) open-source assistants, browsers and accessibility tools, (c) the routing literature and vendor engineering reports; the Home Assistant, Clicky-fork and Chrome/Android hybrid-API sections were researched directly from source code and primary docs.

Headline for the report writer: **no shipped consumer product found in this pass routes between a local small model and a cloud model by confidence, difficulty or latency.** Every shipped system uses one of four rules: (1) a manual model picker, (2) a fixed per-feature assignment (this feature is local, that one is cloud), (3) an availability/eligibility check with fallback (Chrome/Android `prefer_on_device`, Windows `GetReadyState()` cascade, Osaurus), or (4) a deterministic "known command matched locally, else LLM" rule (Home Assistant). Learned or confidence-based routing exists only in research code and cloud-to-cloud routers (RouteLLM, Hybrid LLM, LiteLLM, OpenRouter auto).

---

## Key question 1: Which shipped products do local-first with cloud fallback today, and how do they route?

### Takeaway
Across ~30 products the shipped routing rules are manual pickers, static per-feature splits, or availability checks. The only consumer-facing automatic rule that keys off the *request* rather than the *device* is Home Assistant's "known command matched locally, otherwise LLM" (see KQ2). Dictation vendors have converged on purpose-trained ~0.6 B "cleanup-only" models (Superwhisper S1-mini, Spokenly Cleanup 1) that refuse to behave as chat models, plus length and language caps under which text is passed through unchanged, instead of escalating to a cloud model.

### Inferences
- The dictation market has split the problem differently from the "cascade" framing: rather than escalate hard cases to the cloud, vendors shrink the local task until a 0.6 B model is reliable (cleanup only, English-first, length-capped) and pass the raw text through when outside that envelope. The pass-through is the "fallback", and it is deterministic (length, language, timeout), not confidence-based.
- "Cloud-first, local on request" (Willow Voice, TalkBack's Describe Image) and "local-first, cloud on request" (Raycast, Superwhisper pickers) both exist; neither vendor claims an automatic quality router, which suggests the UX cost of silent model switching (inconsistent output, surprise data egress) is being avoided deliberately — Chrome's docs make the data-egress concern explicit (see KQ3).
- Raycast's forced-cloud features (Extension AI API, Emoji Search, image generation) and Brave's Search-vs-sidebar mismatch show the most common integration bug: a "local" toggle that does not reach every code path.

- Jan "Virtual Models" routing, LM Studio Bionic cloud models: single secondary sources only.

## Key question 2: Home Assistant Assist — the "prefer handling commands locally" design, precisely

### Takeaway
Home Assistant's rule (shipped 2024.12, Dec 2024) is the strongest prior art for a deterministic local-first/LLM-fallback router: on every utterance the pipeline first tries sentence triggers, then strict local intent matching against exposed entities with exact wording, and only if nothing matched (or the match found no targets) does it call the configured LLM conversation agent. There is no confidence score; the "signal" is a strict grammar match plus a filter that withholds two intents from local handling when the LLM has control. Known rough edges: follow-up turns stay with the LLM (by design), and a locally matched intent that fails used to fall through with a confusing chat log until Oct 2026.

### Cited Findings
- **Introduced in 2024.12** under "Let your voice assistant fall back to an LLM-based agent": the pipeline "tries the fast, community-driven default agent first" and "only falls back to an LLM-based agent if no matches are found"; "Specific known commands will be processed locally and extremely fast, and the power of an LLM will only be used for more complex queries that Home Assistant does not natively understand." Rationale: LLMs are "much better at interpreting natural language" but "often slow and/or expensive", and most home commands are simple on/off requests. The screenshot caption calls it "the new option to prefer handling commands locally" in the Assist pipeline dialog. — [HA 2024.12 release post, 2024-12-04](https://www.home-assistant.io/blog/2024/12/04/release-202412/)
- Voice chapter 9 (2025-02-13): the setting "always attempts to run commands with the built-in conversation agent before it sends it off to an LLM"; commands the built-in agent understands (lights) "never reach the LLM", which avoids slowing things down and wasting tokens; an air-quality question is the example that goes to the LLM. — [Voice chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)
- Sept 2025 AI post: "By default, Assist will handle commands first. Only questions or commands it can't understand will be sent to the AI you've set up"; recent commands are shared with the AI so follow-ups ("Add rice") work; handling simple commands first "speeds up response times for simple commands and makes for a more sustainable voice assistant". Streaming test: gemma3:4b on an RTX 3090 with Piper on an i5, "Tell me a long story about a frog": cloud 6.62 s non-streaming vs 0.51 s streaming; Piper 5.31 s vs 0.56 s. Home LLM Leaderboard (Allen Porter): local models using 8 GB+ VRAM "are nearly keeping up" with cloud models. — [HA blog 2025-09-11](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant)
- **Implementing PR #129058** "Handle sentence triggers and local intents before pipeline agent" (synesthesiam, opened 2024-10-23, merged 2024-11-14): adds the `prefer_local_intents` pipeline option; sentence triggers now run regardless of agent (a breaking change: a matching trigger handles the input instead of the LLM). Review debated whether triggers should obey the same toggle (arturpragacz) and whether triggers were being tried twice; balloob asked for full test coverage including error handling. — [PR #129058](https://github.com/home-assistant/core/pull/129058)
- **Code path (dev branch, read 2026-10-27, `homeassistant/components/assist_pipeline/default_pipeline.py` and `conversation/default_agent.py`)**:
  1. `processed_locally = agent_id == HOME_ASSISTANT_AGENT`; if the pipeline agent is *not* the built-in agent and the run is not intent-agent-only, **sentence triggers run first** (`conversation.async_handle_sentence_triggers`); a hit sets `agent_id = "sentence_trigger"`, `processed_locally = True`.
  2. If the LLM agent entity advertises `ConversationEntityFeature.CONTROL`, an `intent_filter` is installed that **excludes `HassGetState` and `HassMediaSearchAndPlay` from local handling** ("we filter out some sentences that are interfering with LLM operation").
  3. If nothing matched yet and `pipeline.prefer_local_intents` is true, `conversation.async_handle_intents(...)` runs; a non-None response sets `agent_id = HOME_ASSISTANT_AGENT`, `processed_locally = True`.
  4. Otherwise "Fall back to pipeline conversation agent" via `conversation.async_converse(...)` with the configured agent.
  The `INTENT_START` event carries `prefer_local_intents` and the debug UI shows "Processed locally: true/false".
- `DefaultAgent.async_handle_intents` docstring: "Only performs strict matching with exposed entities and exact wording. Returns None if no match or a matching error occurred." It calls `async_recognize_intent(user_input, strict_intents_only=True)`, applies the filter, processes the result with `discard_match_errors=True`, and returns None when `response.error_code in _MATCH_ERROR_CODES` ("We ignore no matching errors"). — [default_agent.py (dev)](https://github.com/home-assistant/core/blob/dev/homeassistant/components/conversation/default_agent.py); [default_pipeline.py (dev)](https://github.com/home-assistant/core/blob/dev/homeassistant/components/assist_pipeline/default_pipeline.py)
- **Oct 2026 refinements**: PR #186708 (merged 2026-10-15) "When a pipeline prefers local intents and the matched intent finds no targets, the pipeline falls back to the conversation agent. That agent received a tool call and a failed result it never made. Now neither is written to the chat log." PR #186711 (merged 2026-10-16) warms up intent recognition while the user speaks: "When speech-to-text starts, the pipeline now prepares everything intent recognition needs… With local intents preferred, it is also warmed for LLM pipelines." The dev code comment: "Local intents run on the default agent before the pipeline agent. Without them, loading the language intents would only cost memory." — [PR #186708](https://github.com/home-assistant/core/pull/186708); [PR #186711](https://github.com/home-assistant/core/pull/186711)
- **Follow-up turns stay with the LLM (intentional)**: issue #162768 (opened 2026-02-11, core 2026.2.1): after a local command, correcting a misheard command while in follow-up mode goes to the LLM and the local agent is not re-checked; maintainer arturpragacz: behaviour is "intentional"; closed 2026-02-20, redirected to a feature-request discussion. — [core issue #162768](https://github.com/home-assistant/core/issues/162768)
- **Local match that fails can produce a worse answer than no match**: with local-first on, "What is the weather?" matched the built-in `HassGetWeather` intent even though no weather entity was exposed; the failed intent fell through to the LLM, which "appeared to invent values from the sensors it could access"; the user kept local-first on because it is "a tad bit faster"; later fixed so it "fails correct and follows through to the LLM" (release not stated). HA 2025.12 added visibility into called intents. — [HA community, 2025-12-04](https://community.home-assistant.io/t/my-journey-to-a-reliable-and-enjoyable-locally-hosted-voice-assistant/944860/13)
- **UI confusion**: a user with qwen-2.5 as agent and the toggle on thought commands went to the LLM; the debug view showed "Processed locally: true" — the agent name shown was still qwen. — [HA community, 2026-07-10](https://community.home-assistant.io/t/prefer-handling-commands-locally-does-not-seem-to-work/1016858)
- Community guidance (Nathan Curtis, 2026-08-19): "If it finds a local intent match, it handles the command there and stops"; else "the request falls through to the configured Conversation Agent"; keep the exposed entity set small, "especially for smaller local models"; use a fast model for voice and a larger one for complex requests. — [So You Want to AI in Home Assistant, ch. 9](https://community.home-assistant.io/t/so-you-want-to-ai-in-home-assistant/1021777/9)
- **Speech-to-Phrase** (Feb 2025) is the STT-side analogue: a constrained-vocabulary recogniser that transcribes in under a second on a Raspberry Pi 4 / Home Assistant Green (150 ms on a Pi 5) versus ≥5 s for Whisper on a Pi 4, but "is intended for home control only and not LLMs" — it cannot produce free text, so it cannot feed an LLM fallback. Languages: EN, FR, DE, NL, ES, IT (~70 % of users). — [Voice chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)
- Local LLM support via Ollama has existed since 2024.4; LLM control of the home since 2024.6. — [HA 2024.6 release post](https://home-assistant.io/blog/2024/06/05/release-20246)

### Inferences
- The HA design works because the local tier is a closed grammar: "match" is binary and cheap, so there is no calibration problem. The cost is that a *mis*-match (grammar matched, but intent cannot execute) is indistinguishable from a success until execution, which is exactly the class of bug fixed in PR #186708 and the weather thread.
- The explicit intent filter (withhold `HassGetState`/`HassMediaSearchAndPlay` when the LLM has control) is a hand-tuned "do not let the small tier answer questions it would answer badly" list — the same pitfall class as a small rewrite model answering instead of rewriting.
- Keeping follow-ups with whichever tier answered last is a deliberate consistency choice; it trades a re-check for conversational continuity. For OpenClicky-style assistants, the analogous question is whether a correction after a local answer should re-run the local route.
- Warm-up during STT (PR #186711) is the HA answer to cold-start latency: prepare the local tier while audio is still arriving.

### Gaps
- The exact HA release that fixed the weather fall-through was not identified.
- No official docs page naming the toggle was retrieved; the authoritative wording comes from blog posts, the PR, and the source.

## Key question 3: Platform vendors — Apple, Google (Chrome and Android), Microsoft, Samsung

### Takeaway
All four platform vendors route by **feature assignment and availability**, never by per-request confidence: Apple publishes only "more complex requests … draw on larger, server-based models"; Google's hybrid APIs expose `PREFER_ON_DEVICE` / `PREFER_IN_CLOUD` / `ONLY_*` modes that fall back on *unavailability or unsupported request shape* and explicitly call the first version "rule-based"; Microsoft documents a three-tier readiness cascade (Phi Silica → Foundry Local → Azure OpenAI); Samsung exposes a user toggle that simply disables cloud-only features.

### Cited Findings

**Apple**
- Apple Intelligence (June 2024): "many of the models that power it run entirely on device. To run more complex requests that require more processing power, … Apple Intelligence can flex and scale its computational capacity and draw on larger, server-based models." No router, threshold or split percentage is published. — [Apple Newsroom, 2024-06-10](https://www.apple.com/newsroom/2024/06/introducing-apple-intelligence-for-iphone-ipad-and-mac/); PCC post: cloud is for "advanced features that need to reason over complex data with larger foundation models"; a request carries "the prompt, plus the desired model and inferencing parameters". — [Private Cloud Compute blog, 2024-06-10](https://security.apple.com/blog/private-cloud-compute/)

### Inferences
- Google is the only vendor whose public API is literally "prefer on-device, else cloud", and it defines "else" as *cannot run* (hardware, download in progress, unsupported modality, multi-turn, tool use), never *answered badly*. - Apple's split is baked into features and adapters; developers get an availability enum, a hard 4,096-token budget (the strongest practical "route to cloud" trigger), and from macOS 27 a quota-limited PCC model. The token budget and the "not a chatbot for general world knowledge" statement are the closest things to a published routing policy.
- Microsoft's readiness cascade is the cleanest template for an app: probe tiers at startup in order of privacy/cost, bind once, surface which tier is live.

## Key question 4: What does the literature say about cascade routing — when does a 3 B model suffice, what signals, what savings?

### Takeaway
The literature measures large savings (26 %→14 % of GPT-4 calls at 95 % quality for RouteLLM; 22 % fewer GPT-3.5 calls at a 1 % drop for Hybrid LLM; 50–60 % cost cuts for consistency/self-verification cascades on reasoning) but almost entirely for 7–13 B "small" models against cloud models on QA/reasoning. The one row with a sub-1 B small model (FLAN-T5-800M → Llama-2-13B) loses 10–14 quality points at 40 % offload, and confidence signals from ≤1 B models are reported as near-random; no paper measures confidence-based deferral for 1–4 B instruction models on rewrite/summarise/classify.

### Cited Findings
- **FrugalGPT** (Chen, Zaharia, Zou, May 2023): learned scoring function per output plus per-stage thresholds; "match the performance of the best individual LLM (e.g. GPT-4) with up to 98% cost reduction or improve the accuracy over GPT-4 by 4% with the same cost"; 12 commercial APIs, cloud-to-cloud. — [arXiv 2305.05176](https://arxiv.org/abs/2305.05176)
- **Hybrid LLM** (Ding et al., Microsoft, ICLR 2024): DeBERTa-v3-large (300 M) router predicts the BART-score quality gap; labels deterministic / probabilistic (10 samples) / transformed (margin t). Quality drop vs all-large at 20 % / 40 % fewer large calls: Llama-2-7B→13B 0.0–0.2; Llama-2-13B→GPT-3.5 0.8–1.0 / 2.9–3.5; **FLAN-T5-800M→Llama-2-13B 4.7–5.8 / 10.3–13.8**; 22 % fewer GPT-3.5 calls at a 1 % drop. — [arXiv 2404.14618](https://arxiv.org/html/2404.14618v1); [ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/b47d93c99fa22ac0b377578af0a1f63a-Abstract-Conference.html)
- **RouteLLM** (Ong et al., LMSYS, Jun 2024 / ICLR 2025): routers trained on Chatbot Arena preference data (similarity-weighted Elo, matrix factorisation, BERT, causal LLM); MF router reaches **95 % of GPT-4 performance with 26 % of calls to GPT-4**, 14 % with augmented data (~75 % cheaper than random); GPT-4 vs Mixtral-8x7B; routers transferred to Claude-3-Opus vs Llama-3-8B without retraining; `pip install routellm`. — [LMSYS blog 2024-07-01](https://lmsys.org/blog/2024-07-01-routellm/); [arXiv 2406.18665](https://arxiv.org/abs/2406.18665v4)
- **LLM Cascades with Mixture of Thought** (Yue et al., ICLR 2024): answer consistency across CoT/PoT samples; GPT-4-level performance "while requiring only 40% of its cost" (GPT-3.5→GPT-4, reasoning). — [ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/5de11e930c1bbfda5d4fc9d2b0924032-Abstract-Conference.html)
- **AutoMix** (Aggarwal, Madaan et al., NeurIPS 2024): few-shot self-verification by the small model, POMDP router over the noisy signal; "reduced computational cost by over 50% for comparable performance". — [NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/ecda225cb187b40ea8edc1f46b03ffda-Abstract.html); [arXiv 2310.12963](https://arxiv.org/abs/2310.12963v4)
- **Token-level uncertainty cascades** (Gupta et al., Google, ICLR 2024): sequence-level confidence (product/mean of token probs) is "strongly sub-optimal because of a length bias"; quantiles of per-token uncertainty improve the cost–quality curve; adding embeddings to a learned deferral rule helps further; FLAN-T5 pairs, includes summarisation. — [arXiv 2404.10136](https://arxiv.org/html/2404.10136v1)
- **Speculative cascades** (Narasimhan et al., Google, ICLR 2025; blog Sept 2025): token-level deferral during speculative decoding; requires both models co-located, so not a device↔cloud design. — [Google Research blog](https://research.google/blog/speculative-cascades-a-hybrid-approach-for-smarter-faster-llm-inference/)
- **Gatekeeper** (Google, Feb 2025): fine-tune the small model's confidence to be high when correct and low when not ("I know what I don't know"). — [arXiv 2502.19335](https://arxiv.org/html/2502.19335v3)
- **Arch-Router** (Katanemo, Jun 2025): a 1.5 B generative router (Qwen2.5-1.5B fine-tune) maps queries to user-defined domain/action policies; 93.17 % routing accuracy, 7.71 pts above GPT-4o/Claude-3.7 as routers; base Qwen2.5-1.5B 20.69 %. The router itself is small enough to run locally. — [arXiv 2506.16655](https://arxiv.org/pdf/2506.16655)
- **RouterBench** (Hu et al., Martian, Mar 2024) — [arXiv 2403.12031](https://arxiv.org/html/2403.12031v2); **RouterArena** (Oct 2025) — [arXiv 2510.00202](https://www.arxiv.org/pdf/2510.00202); survey "Dynamic Model Routing and Cascading for Efficient LLM Inference" (Mar 2026) — [arXiv 2603.04445](https://arxiv.org/pdf/2603.04445)
- **Small-model confidence**: "Provable Limits and Certified Deferral for Verbalized Uncertainty in Small Language Models" (Aug 2026) studies risk-controlled deferral at 0.5 B–14 B — [arXiv 2608.05064](https://arxiv.org/pdf/2608.05064); ScaleCal preprint: normalised entropy "collapses to near-random discrimination at 1B and below" — [Research Square](https://www.researchsquare.com/article/rs-10911915); honesty survey separating calibration from selective prediction — [arXiv 2409.18786](https://arxiv.org/pdf/2409.18786)
- **Local latency/memory (community, uncontrolled)**: Llama-3.2-3B-Instruct 4-bit on M1 16 GB via oMLX ≈24 tok/s, ≈14 s TTFT at a full 4K context, 2.6 GB peak — [omlx benchmark](https://omlx.ai/benchmarks/mbvpbdbf); ≈30 tok/s Q4_K_M via Ollama on M1 16 GB — [table](https://kunalganglani.com/llm-benchmarks); MLX 4-bit build is a 1.8 GB download — [Willison 2025-02-15](https://simonwillison.net/2025/Feb/15/llm-mlx); MLX 15–37 % faster generation than llama.cpp but llama.cpp has lower TTFT and a quantised KV cache, recommended for 8–16 GB — [guide](https://hermes-agent.nousresearch.com/docs/guides/local-llm-on-mac). Clicky Local Mode PR measured Llama-3.2-3B-Instruct-4bit on an M1 Pro 16 GB: first token 0.6–0.7 s, 54–60 tok/s, 3.0 s model load from disk, 1.8 GB download (see KQ6). — [farzaa/clicky #115](https://github.com/farzaa/clicky/pull/115)

### Inferences
- Signal taxonomy actually used: (a) availability/eligibility (all vendors), (b) static task assignment (Apple, Windows, Samsung, dictation vendors), (c) learned pre-router on the prompt (Hybrid LLM, RouteLLM, Arch-Router), (d) post-hoc confidence from the small answer (FrugalGPT, token quantiles, AutoMix, MoT, Gatekeeper), (e) hard token budgets (Apple 4,096, Phi Silica 2K, Nano 9,216), (f) error class (LiteLLM). Only (a), (b), (e), (f) have shipped to consumers.
- Post-hoc confidence costs the local model's full latency before escalation and is unreliable at ≤1 B; a pre-router or a static task split is the better fit for a 0.6–3 B tier. The web.dev "capability-based escalation" pattern (a small classifier decides common vs uncommon) is the published consumer-facing version of (c).
- Every academic saving number shrinks as the capability gap widens; the 800 M→13 B row is the closest proxy for "on-device 1–3 B vs frontier cloud" and argues for keeping the local tier on narrow transformations rather than open Q&A.

### Gaps
- No primary source measures confidence-based deferral for 1–4 B instruction models on rewrite/summarise/classification.
- RouterBench counts, AutoMix model pairs and the 3.3 B Phi Silica figure were reported from memory by the sub-researcher and should be re-checked against PDFs before citing.
- No controlled cold-start or memory numbers for 8 GB laptops; only community 16 GB figures.
- "Online Cascade Learning" (ICML 2024), GraphRouter, RouterDC, MixLLM, Universal Model Routing were confirmed only as citations.

## Key question 5: Accessibility- or older-adult-focused assistants doing local+cloud hybrids

### Takeaway
The clearest accessibility precedent is Google TalkBack: Gemini Nano describes images on device (offline), and the user can *ask* for a richer cloud description ("Describe Image" → Gemini 1.5 Flash) — escalation is user-triggered, not automatic. Envision moved scene description and text reading on device with Gemma 4 in April 2026. No older-adult assistant with a documented hybrid was found.

### Cited Findings
- TalkBack (Sept 2024): multimodal Gemini Nano on device for image descriptions, works offline, replaced the "Garcon" model; image input 768 px chosen (first token ≈2 s later than 512 px; tokens streamed to TTS); **"Describe Image" in the three-finger-tap menu sends the image to server-side Gemini 1.5 Flash for more detail — cloud is user-invoked.** — [Android Developers Blog, 2024-09](https://android-developers.googleblog.com/2024/09/talkback-uses-gemini-nano-to-increase-low-vision-accessibility.html)
- Envision (Apr 2026): scene description and text reading now on device with Google Gemma 4 on Arm, works offline; previously cloud. — [Envision blog, 2026-04](https://www.letsenvision.com/blog/envision-arm-and-google-are-bringing-powerful-visual-ai-on-device)
- Be My AI (Be My Eyes): cloud GPT-4-vision class model since 2023; no local tier found. — [glossary (weak source)](https://a11y-paradise.onrender.com/glossary/69abb6417cf68de1a5b026e2)
- Clicky fork PR #115 motivates Local Mode partly on cost for users without an API budget ("the 14-year-old in Lagos doesn't need an API budget") and privacy ("no screenshot, no upload, nothing to leak") — not accessibility-specific but relevant to low-resource users. — [farzaa/clicky #115, 2026-06-15](https://github.com/farzaa/clicky/pull/115)

### Inferences
- "Local answer immediately, cloud on explicit request" (TalkBack) is a defensible pattern for blind and low-vision users because it keeps latency low and makes data egress a deliberate act; it also avoids the inconsistency of silently switching models mid-conversation.

### Gaps
- Seeing AI on-device channels, Apple VoiceOver Screen Recognition (believed on-device only, unverified here), ElliQ, Dot and academic older-adult systems: no primary evidence found.
- TalkBack 2025–26 updates (follow-up questions about images) not verified.

### Inferences
- The forks confirm the same shape as the commercial products: manual picker now, routing later. The explicit "no screenshot in Local Mode" rule is a useful statement of a *capability* boundary (local tier cannot see the screen) rather than a quality boundary.
- The 120 s `waitsForConnectivity` hang called out in #115 is a concrete failure of cloud-first without an offline probe; a fast reachability check (as in #28's 0.5 s pre-flight) is the minimum needed for any cloud→local fallback.

## Key question 7: Design pitfalls reported in practice

### Takeaway
The recurring, sourced pitfalls are: the small model answering the dictation instead of rewriting it; small models ignoring prompts or over-editing; memory held by an always-loaded local LLM; cold-start and first-run slowness; hard length caps; English-first coverage; "local" toggles that miss some code paths; and local tiers that fail rather than fall back when offline.

### Cited Findings
- **Answers instead of rewriting.** Paraspeech user (2026-02-11): with rewrite on, dictating "which model are you" produced "I am Claude"; off, dictation was correct; founder (2026-03-26): "a limitation of the LLM and the prompt", smarter models integrated, cloud LLM coming. — [Paraspeech board](https://paraspeech.userjot.com/board/p/when-rewriting-transcribed-dictation-thinks-i-m-asking-it-a). AssemblyAI's rewrite docs: the model "will occasionally answer a question it heard in the audio instead of rewriting it". — [AssemblyAI transcript rewriting](https://www.assemblyai.com/docs/dictation/transcript-rewriting.md). OpenWhispr: if cleanup changes tone, answers questions or follows dictated instructions, "the voice agent may be running instead". — [OpenWhispr cleanup](https://docs.openwhispr.com/help/dictation/cleanup.md). Vendor mitigations: purpose-trained models that "do not follow instructions or answer questions" (Spokenly Cleanup 1) and are "not a chat model" (S1-mini); S1-mini's card warns that changing the system prompt wording can cause hallucinated or garbled output and requires a control line with Styling/Structure/Context axes. — [Spokenly docs](https://spokenly.app/docs/macos/local-model-cleanup); [S1-mini guide](https://betterstack.com/community/guides/ai/s1-mini.md)
- **Prompt-ignoring and over-editing.** Handy: "small models (under 3B parameters) may ignore prompts"; reasoning models leak tags. — [Handy docs](https://handy.computer/docs/post-processing). Koe: local LLM "loves to paraphrase, and sometimes to translate". — [dev.to](https://dev.to/dkamehat/i-built-koe-fully-local-offline-voice-dictation-for-windows-faster-whisper-ollama-jal). Khoj skipped the offline JSON-extraction step because the small model could not emit reliable JSON. — [Khoj PR #680](https://github.com/khoj-ai/khoj/pull/680)
- **Memory pressure.** Superwhisper user (16 GB M4 Mac mini, 2026-08-31): S1-mini "still sits at about 900 MB in Activity Monitor" after long idle while the voice model unloads on a timer; requests idle-unload; no developer reply. — [Superwhisper board](https://superwhisper.userjot.com/board/p/let-s1-mini-unload-when-superwhisper-is-idle). Spokenly: ~600 MB during dictation, up to 1 GB. — [Spokenly docs](https://spokenly.app/docs/macos/local-model-cleanup). Osaurus recommends ≥8 GB for Apple's model. — [Osaurus](https://docs.osaurus.ai/models/apple-intelligence). Community: "with 16GB you're going to hit swap if you keep whisper + 8B + TTS all warm". — [Reddit snapshot](https://reddit.sentinel-team.org/posts/1uuzb1h/snapshots/2026-07-17T18%3A53%3A30.39359Z). Chrome: 22 GB disk, >4 GB VRAM or 16 GB RAM; Edge: 5.5 GB VRAM; Windows Recall: 16 GB RAM. (KQ3 sources.)
- **Cold start.** Spokenly: first dictation after a macOS update and the first long dictation take several seconds longer. — [Spokenly docs](https://spokenly.app/docs/macos/local-model-cleanup). Clicky #115: 3.0 s model load from disk, 1.8 GB first download. — [#115](https://github.com/farzaa/clicky/pull/115). Firebase: on-device model download "can take several minutes"; PREFER modes go to cloud meanwhile. — [Firebase hybrid](https://firebase.google.com/docs/ai-logic/hybrid-on-device-inference). Home Assistant warms intent recognition during STT (PR #186711). Osaurus: Apple's model "may be briefly unavailable during macOS updates or model downloads".
- **Length caps.** Spokenly >1,600 words (>100 on macOS 15) unchanged; Apple 4,096 tokens shared in/out; Phi Silica 2K; Nano 9,216; Open Interpreter local 3,000. (Sources above.)
- **Language coverage.** S1-mini English-only v1; Spokenly best in English, six others at lower quality, rest untouched; Chrome Nano EN/ES/JA/DE/FR from Chrome 149; Apple framework unavailable when the device language is unsupported; Speech-to-Phrase six languages. (Sources above.)
- **"Local" that is not everywhere.** Raycast: Extension AI API, Emoji Search and image generation still reach Raycast servers with a local model chosen. — [Raycast manual](https://manual.raycast.com/ai/local-models.md). Brave: BYOM in the sidebar but not Search "Answer with AI". — [Brave community](https://community.brave.app/t/brave-search-leo-ai-with-local-llm-via-ollama/605914). Clicky #115 notes the upstream analytics layer sent full transcripts to PostHog, gated only by the new Local Mode. — [#115](https://github.com/farzaa/clicky/pull/115)
- **Offline = fail, not fall back.** Handy: offline post-processing fails, transcription still works. — [Handy FAQ](https://handy.computer/docs/faq). Clicky upstream: 120 s `waitsForConnectivity` hang before #115. OpenWhispr and Voxtype degrade to raw text (sources above).
- **Fallback that makes things worse.** Home Assistant weather intent matched locally, failed, and the LLM then "invented values" (KQ2). Firebase's own caution: cloud fallback "may have legal or functional consequences". — [Chrome Firebase page](https://developer.chrome.com/docs/ai/firebase-ai-logic)
- **Voice/consistency between tiers.** web.dev recommends "the same model on both sides" when only fallback is needed, "for consistency and lower maintenance". — [web.dev](https://web.dev/learn/ai/platform). Home Assistant keeps follow-ups with the tier that answered last (issue #162768). No paper or vendor note specifically on local-vs-cloud "voice" mismatch was found.
- **Apple Writing Tools quality reports (not routing-specific):** a "friendly" rewrite that lost the original intent; rewrites sometimes "not aggressive enough". — [Kirkville](https://kirkville.com/the-big-problem-with-apples-ai-writing-tools/); [Laptop Mag](https://www.laptopmag.com/ai/i-tried-apple-intelligence-on-my-mac-it-could-change-the-way-you-use-macos)

### Inferences
- The cheapest, most robust guards used in shipped products are deterministic: output-only prompt plus temperature 0, a length-ratio sanity check with pass-through, a timeout with pass-through, a reachability pre-flight before cloud calls, and idle unload of the local model. None requires a calibrated confidence score.
- For a product like OpenClicky the pitfalls cluster into two design rules: (1) give the local tier only transformations with a checkable output shape (rewrite, cleanup, classify, extract), never open Q&A about the screen; (2) make every escalation visible (badge or spoken cue) so inconsistent voice is attributable rather than confusing.

### Gaps
- No Reddit/HN threads specifically about 8 GB Macs or first-load latency for dictation apps were found; only adjacent anecdotes.
- No source quantifies how often a 0.6–3 B rewrite model answers instead of rewriting; only anecdotes and vendor warnings.
- No published UX study of inconsistent output between local and cloud tiers.
