# Windows built-in on-device AI for third-party desktop apps (Microsoft Foundry on Windows / Windows AI APIs / Phi Silica / Foundry Local / Windows ML)

Research date: 2026-10-27. All Microsoft Learn pages were fetched live; `ms.date` values are quoted so the writer can judge freshness. Naming note up front: "Windows Copilot Runtime" (2024) and "Windows AI Foundry" (2025) are both superseded names; the current umbrella brand is **"Microsoft Foundry on Windows"** = Windows AI APIs + Foundry Local + Windows ML — [Choose your Windows AI solution, terminology decoder, ms.date 2026-08-05](https://learn.microsoft.com/en-us/windows/ai/windows-ai-comparison). The docs themselves still use "Windows AI Foundry" in places (e.g. the APIs index page), so expect both names.

Headline finding the writer should not miss: **Phi Silica is being retired.** The Phi Silica page (ms.date 2026-10-16) says "Phi Silica is being replaced by Aion Instruct, a new on-device model"; Aion Instruct rolls to Windows Insiders in **November 2026** and to retail in **January 2027**, "at which point Phi Silica will be removed" — [Phi Silica in the Windows App SDK](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica). The `LanguageModel` API surface stays; the model behind it changes.

## KQ1. Is Phi Silica / `Microsoft.Windows.AI.Text.LanguageModel` generally available in late 2026, and is it NPU-only? What happens on an ordinary x64 laptop?

### Takeaway
The `LanguageModel` API is in the **stable** Windows App SDK channel (since 1.8.0, Sept 2025) but was gated as a **Limited Access Feature (LAF)** requiring a Microsoft-issued token until literally today: Windows App SDK **2.6.4 (released 2026-10-27)** drops the LAF unlock requirement. On a Copilot+ PC (40+ TOPS NPU) the model is preinstalled and runs on the NPU; on an ordinary x64 laptop it runs **only** if there is an NVIDIA RTX 30-series+ or AMD RX 9060+ GPU with 6 GB+ VRAM, and even then only on a Windows Insider Experimental build with Developer Mode and an experimental SDK — i.e. in practice, an NPU-less laptop with integrated graphics gets `NotSupportedOnCurrentSystem` and nothing else. CPU execution is explicitly "Not supported".

### Inferences
- For a shipping app today (2026-10-27): target stable Windows App SDK 2.6.4 and you avoid the LAF token entirely; anything older than 2.6.4 needs the token. The docs lag the release notes by days; expect the Phi Silica page to be rewritten.
- "NPU-only" is no longer strictly true, but the GPU path is effectively developer-preview-only (Insider Experimental build + Developer Mode + experimental SDK + vendor beta driver). For the installed base of ordinary x64 laptops with integrated graphics, the correct expectation is `NotSupportedOnCurrentSystem` and your own fallback. Aion Instruct's stated CPU inference (in Edge) suggests the Windows AI API path may reach CPU-only PCs in 2027, but Microsoft has not said that for the Windows App SDK API.
- Building against `LanguageModel` now is reasonable precisely because the API is model-agnostic; the Jan 2027 swap to Aion Instruct is Microsoft's problem, but re-test prompts and LoRAs (Microsoft explicitly says re-train LoRAs with Foundry Toolkit).

### Gaps
- No Microsoft statement on whether Aion Instruct via the Windows App SDK `LanguageModel` API will run on CPU-only PCs, or on which GPU/NPU tiers; only the Edge-side claim exists.
- Aion 1.0 Instruct parameter count and context length are not published in any Microsoft source found (secondary blogs give conflicting numbers; not reported here).
- No published LAF approval criteria or turnaround times.

## KQ2. What is Foundry Local, does it fill the gap on non-Copilot+ PCs, does it ship with Windows, licensing and catalog?

### Takeaway
Foundry Local is Microsoft's cross-platform, in-process ONNX Runtime-based local LLM/ASR stack with an OpenAI-compatible API, GA since **2026-04-09**, runs on CPU/GPU/NPU on Windows, macOS (Apple silicon) and Linux, needs no Azure account, no LAF token and no NPU, and is the documented fallback tier below Phi Silica. It does **not** ship inside Windows: the ~20 MB runtime is bundled into your app via NuGet/pip/npm (the CLI is an optional separate winget install). The SDK is MIT, the CLI is under Microsoft Software License Terms, and each model carries its own license.

### Cited Findings
- GA date: "the General Availability (GA) of Foundry Local" announced April 9, 2026; "cross platform: Windows, Linux and macOS"; "no cloud dependency or per-token costs"; acceleration "GPU, NPU, or CPU fallback"; SDK packages: JavaScript `foundry-local-sdk` (npm), Python `foundry-local-sdk` / `foundry-local-sdk-winml` (recommended on Windows), C# `Microsoft.AI.Foundry.Local` (NuGet), Rust `foundry-local-sdk`; "the Foundry Local Core and ONNX Runtime binaries are bundled into the app at build time", "end users need no separate CLI or third-party app install"; inference APIs follow OpenAI chat completions / audio transcription and "the Open Responses API format"; integrates with Windows ML "to get hardware-matched execution provider plugins through OS/Windows updates" — [Foundry Local GA, Microsoft Foundry Blog, 2026-04-09](https://devblogs.microsoft.com/foundry/foundry-local-ga/)
- Secondary sources date GA to Build 2026 (June 2) instead; Microsoft's own blog says April 9 — [byteiota](https://byteiota.com/microsoft-foundry-local-ga/) vs [Microsoft Foundry Blog](https://devblogs.microsoft.com/foundry/foundry-local-ga/). Treat April 9 as authoritative.
- What it is (Azure docs, ms.date 2026-05-15, updated 2026-10-19): "an end-to-end local AI solution for shipping applications that run entirely on your device"; "The runtime adds approximately 20 MB to your application package"; catalog "covers chat completions (for example, GPT OSS, Qwen, DeepSeek, Mistral, and Phi) and audio transcription (for example, Whisper)"; "Models are versioned, so your application can pin to a specific version or automatically receive updates"; "detects the hardware available on your device and selects the best execution provider ... falls back to CPU seamlessly"; "Is an Azure subscription required? No."; "Foundry Local runs inference entirely on the device"; network used only for model/EP downloads and optional diagnostics; "Foundry Local is optimized for hardware-constrained devices where a single user accesses the model at a time" (not a server stack) — [What is Foundry Local?](https://learn.microsoft.com/en-us/azure/foundry-local/what-is-foundry-local)
- Windows-specific prerequisites (Windows docs, ms.date 2026-09-21): "Windows 11, version 24H2 (build 26100) or later; .NET 9.0 SDK or later; An x64 or Arm64 device with enough memory and disk space for the model you select; Internet access for the initial package, model, and runtime-component downloads." "A dedicated GPU, NPU, or Copilot+ PC isn't required when the selected model has a compatible CPU variant." "No special permissions or unlock tokens are required. The native SDK runs in your app process and doesn't require the Foundry Local CLI or a separate local REST server. The same pattern works in a console app, a WinUI 3 app, a WPF app, or any other .NET host." Windows NuGet: `Microsoft.AI.Foundry.Local.WinML` (uses Windows ML execution providers); cross-platform: `Microsoft.AI.Foundry.Local`. Optional CLI: `winget install Microsoft.FoundryLocal`. Model aliases resolve to hardware variants: "a QNN NPU variant on Snapdragon, a CUDA variant on NVIDIA, or a CPU variant" — [Get started with Foundry Local (Windows)](https://learn.microsoft.com/en-us/windows/ai/foundry-local/get-started)
- Note the OS discrepancy: the Microsoft Foundry on Windows overview table says Foundry Local supports "Windows 10 and later PCs and cross-platform" — [Use local AI with Microsoft Foundry on Windows, ms.date 2026-07-24](https://learn.microsoft.com/en-us/windows/ai/overview) — while the Windows get-started (WinML NuGet path) requires Windows 11 24H2. Likely the WinML-accelerated package is 24H2+, the plain package is broader; not stated explicitly.
- Quickstart model is `phi-4-mini` ("currently the latest Microsoft Phi model available through the Foundry Local alias"), and the docs stress "Phi-4 Mini is separate from Phi Silica, the Windows AI API model that ships with Windows" — [Get started with Foundry Local (Windows)](https://learn.microsoft.com/en-us/windows/ai/foundry-local/get-started)
- Licensing (GitHub README): "Foundry Local SDK is licensed under the MIT license." "Foundry Local CLI is licensed under the Microsoft Software License Terms." "Individual models made available for use with Foundry Local are subject to the each model's license terms." Latest CLI listed: `cli-preview-0.11.0` (public preview). Tool calling appears in C#, JS, Python and Rust samples; "Used by" section is empty — [microsoft/Foundry-Local](https://github.com/microsoft/Foundry-Local)
- Catalog size: "20+ OSS LLM models via Foundry Local", browse at foundrylocal.ai/models — [Ready-to-use local LLMs on Windows, ms.date 2026-01-13](https://learn.microsoft.com/en-us/windows/ai/apis/local-llms)
- Streaming and generation parameters are exposed in the C# SDK (`CompleteChatStreamingAsync`, `Settings.Temperature/MaxTokens/TopP`) — [Get started with Foundry Local (Windows)](https://learn.microsoft.com/en-us/windows/ai/foundry-local/get-started)
- Microsoft's decision tree: "If Windows AI APIs don't have what you need, or you need to support Windows 10 and later, consider Foundry Local for LLM or voice-to-text scenarios." — [Microsoft Foundry on Windows overview](https://learn.microsoft.com/en-us/windows/ai/overview)
- A Python pitfall: "The `foundry-local` package on PyPI (without `-sdk`) is an unrelated third-party package." — [Get started with Foundry Local (Windows)](https://learn.microsoft.com/en-us/windows/ai/foundry-local/get-started)

### Inferences
- Foundry Local is the realistic "runs on any customer's PC" rung for a WPF app: in-process, no token, no NPU. Cost is a multi-GB first-run model download that you must gate with consent, and quality/latency depends on the user's CPU/GPU (Phi-4-mini-class models on CPU are usable but slow on thin laptops; no Microsoft latency numbers were published).
- Because it is bundled, Foundry Local models are not "shared across apps" by the OS the way Phi Silica is, despite the overview table claiming "shared across apps"; the GA blog's "bundled into the app at build time" wording and the Azure FAQ both describe an in-process design. Writer should present this carefully.

### Gaps
- No official list of the execution providers by vendor (QNN, CUDA, OpenVINO, VitisAI) was found on the pages fetched; only "QNN NPU variant on Snapdragon, CUDA on NVIDIA, or CPU" is named.
- No Microsoft-published performance numbers (tokens/s) for Foundry Local models.
- Foundry Local version 2.1.0 (2026-09-30) claimed by a third-party tracker was not verified against Microsoft sources.

## KQ4. Microsoft's own hybrid local/cloud guidance (and the Oct 2026 "hybrid intelligence" platform)

### Takeaway
Microsoft now has an explicit, dated doc for hybrid routing (updated 2026-10-14): local-first, readiness-gated, consent-gated model downloads, cloud only when policy allows, and additionally **route by task complexity** (classification/rewrite/summarize/extraction/short-input tasks local; multi-step reasoning, long context, broad knowledge, high-accuracy tasks cloud). The platform-level "hybrid intelligence" announced 2026-10-07 (HydraFusion router, Copilot using local models, llama.cpp in Windows ML) is for Microsoft's own Copilot/GitHub Copilot and is not yet offered to third-party apps as an API.

### Cited Findings
- Core statement: "Many production apps use a hybrid strategy: try a local Windows AI API or local model first, then fall back to a cloud endpoint when the model isn't installed, the device isn't supported, the user doesn't consent to a model download, or the task requires a larger model." — [Choose between cloud-based and local AI models, ms.date 2026-10-14](https://learn.microsoft.com/en-us/windows/ai/cloud-ai)
- Hybrid design steps (same page): "1. Choose the local capability first ... 2. Check readiness before use ... 3. Ask for consent when a local model must be downloaded. Some local models are optional and can be several GB ... 4. Define a cloud fallback. If the local model isn't ready, call a cloud endpoint only when the user and organization allow data to leave the device. Keep the local and cloud paths behind the same app-level abstraction ... 5. Keep behavior observable. Log which path was used ... without logging prompts, tokens, or sensitive content" — [cloud-ai](https://learn.microsoft.com/en-us/windows/ai/cloud-ai)
- Route by task complexity: "Favor the local model for tasks such as: Short, single-turn classification or intent detection ...; Rewriting, summarizing, or reformatting short, well-structured text that fits comfortably within the local model's context window; Extracting structured data (for example, a table or key fields) from a short, clean input; Low-risk conversational responses ...; Any scenario where the task must work offline". "Favor a cloud-based model for tasks such as: Multi-step reasoning, planning, or tasks that chain several tool calls together; Long-document or multi-turn scenarios that exceed the local model's context window; Tasks that require broad general knowledge ...; Scenarios with a high accuracy bar ...; Complex code generation, image generation". Implementation: "Classify the task before you pick a model. Use simple, explicit signals you control — the feature or UI entry point, input length, or a lightweight local classification step"; "Route directly to the cloud path for tasks you've classified as advanced, instead of attempting local inference first and discarding a low-quality result"; "Let users escalate"; optionally use a decision model such as Microsoft-Decision-1 (cloud) — [cloud-ai](https://learn.microsoft.com/en-us/windows/ai/cloud-ai)
- Three-tier code sample: try `LanguageModel.GetReadyState()` / `EnsureReadyAsync()`; else `foundryClient.IsModelAvailableAsync("phi-4-mini")`; else "Fall back to Azure AI (always available)" — [Choose your Windows AI solution](https://learn.microsoft.com/en-us/windows/ai/windows-ai-comparison)
- Transparency note: "Implement timeouts and fallbacks: For scenarios where response time is critical, implement appropriate timeouts and consider offering cloud-based fallback options (with user consent)." — [Transparency Note](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica-transparency-note)
- Tooling named for cloud side: Microsoft Foundry, Azure AI Services, Azure OpenAI; "integrate seamlessly with Azure DevOps, GitHub Copilot, Semantic Kernel" — [cloud-ai](https://learn.microsoft.com/en-us/windows/ai/cloud-ai). Foundry Toolkit for VS Code (formerly AI Toolkit) handles model playground, fine-tuning "both locally or in the cloud", and deploy "either to the cloud or with an application that runs on a device" — [Microsoft Foundry on Windows overview](https://learn.microsoft.com/en-us/windows/ai/overview)
- Microsoft.Extensions.AI abstraction in practice: AI Dev Gallery's `PhiSilicaClient`, `FoundryLocalChatClientAdapter` and `OpenAIModelProvider` all implement/produce `IChatClient` — [microsoft/ai-dev-gallery](https://github.com/microsoft/ai-dev-gallery). There is no Microsoft-shipped NuGet `IChatClient` for Phi Silica found; the sample is the reference.

## KQ5. Can an unpackaged WPF .NET 8 app consume the Windows App SDK AI APIs? Requirements.

### Takeaway
Officially yes for WPF/WinForms (the get-started page has WPF and WinForms tabs targeting `net8.0-windows10.0.22621.0`), **but the AI APIs need package identity plus the `systemAIModels` capability**, so in practice the WPF app must be packaged (MSIX or packaged-with-external-location/sparse) rather than a plain xcopy exe; the docs' WPF tab is internally inconsistent on this. Target Windows 11 24H2+ (25H2 build 26200.7309+ per troubleshooting), stable SDK 2.6.4 (or 2.5.1+ with LAF token), `MaxVersionTested` 10.0.26226.0, and ensure the Windows App SDK runtime is initialized/installed.

### Cited Findings
- WPF tab project settings: `<TargetFramework>net8.0-windows10.0.22621.0</TargetFramework>`, `<RuntimeIdentifiers>win-x86;win-x64;win-arm64</RuntimeIdentifiers>`, `<UseWPF>true</UseWPF>`, `<WindowsPackageType>None</WindowsPackageType>`; then "Edit the Package.appxmanifest file ... add ... `<systemai:Capability Name="systemAIModels"/>`", namespace `xmlns:systemai="http://schemas.microsoft.com/appx/manifest/systemai/windows10"`, "The max version tested in the TargetDeviceFamily element ... needs to be at least 10.0.26226.0", plus `<AppxOSMinVersionReplaceManifestVersion>false</AppxOSMinVersionReplaceManifestVersion>` and `<AppxOSMaxVersionTestedReplaceManifestVersion>false</AppxOSMaxVersionTestedReplaceManifestVersion>` in the csproj; NuGet "latest Stable Windows App SDK version, such as 2.5.1 or later" (experimental 2.2.2-experimental9+ for GPU). Same code as WinUI: `LanguageModel.GetReadyState()`, `EnsureReadyAsync()`, `CreateAsync()`, `GenerateResponseAsync(prompt)` — [Get started building an app with Windows AI APIs, ms.date 2026-10-14](https://learn.microsoft.com/en-us/windows/ai/apis/get-started)
- Identity requirement: "Apps that use Windows AI APIs need to be granted package identity at runtime ... If you are seeing an UnauthorizedAccessException error (or having other access issues), ensure that your app is packaged and the systemAIModels capability was added to your manifest file". Also: "Self-contained apps cannot run from the Downloads folder (or from anywhere under the C:\Users folder)." — [Windows API troubleshooting](https://learn.microsoft.com/en-us/windows/ai/apis/troubleshooting)
- Microsoft moderator advice (Feb 2026): "Use a Packaged WinUI 3 app with the Windows App SDK ... instead of plain WPF"; community: "the package must be installed on the system, not just registered for debugging"; check generated `AppxManifest.xml` because tooling "can 'helpfully' change the MaxVersionTested value" — [Microsoft Q&A](https://learn.microsoft.com/en-au/answers/questions/5761829/is-it-possible-to-create-a-desktop-application-tha)
- Unpackaged apps must bootstrap the runtime: "By default, a WPF, WinForms, or Win32 desktop app is unpackaged. An unpackaged app must initialize the Windows App SDK runtime before using any other feature of the Windows App SDK" (search summary of Microsoft Learn; see [Use the Windows App SDK in an existing project](https://learn.microsoft.com/en-my/WINDOWS/APPS/windows-app-sdk/use-windows-app-sdk-in-existing-project) and [Configure your WPF project for Windows App SDK support](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/wpf-plus-winappsdk#configure-your-wpf-project-for-windows-app-sdk-support))
- Package identity for unpackaged apps: packaging "with external location (Sparse packaging)" is Microsoft's low-friction route when hitting `APPMODEL_ERROR_NO_PACKAGE`; "if AI APIs are on your roadmap, consider starting packaged" (search summary citing [Windows developer glossary / packaging docs](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-glossary))
- Experimental-channel apps cannot ship via Store: "Experimental features are not supported for use in production environments and apps that use them cannot be published to the Microsoft Store." — [Windows API troubleshooting](https://learn.microsoft.com/en-us/windows/ai/apis/troubleshooting)
- Foundry Local, by contrast, explicitly supports plain WPF: "The same pattern works in a console app, a WinUI 3 app, a WPF app, or any other .NET host" with `net9.0-windows10.0.26100.0` (its quickstart requires .NET 9) — [Get started with Foundry Local (Windows)](https://learn.microsoft.com/en-us/windows/ai/foundry-local/get-started)
- 2.6.4 removes the LAF unlock for Language Model APIs (see KQ1) — [Windows App SDK 2.x release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable)
- `AICapabilities.HasAICapability` (2.1.3) lets apps "determine whether the device is a Copilot+ PC" — [Windows App SDK 2.x release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable)

### Inferences
- For OpenClicky's shape (Windows client is WPF, currently unsigned/unpackaged): using Phi Silica/Aion requires taking on MSIX or sparse packaging plus the `systemAIModels` capability; Foundry Local requires neither (but .NET 9 for its quickstart, and a per-app model download). `WindowsPackageType=None` in the WPF tab is inconsistent with editing an appxmanifest and with the troubleshooting page's identity requirement; writer should flag this as a documentation contradiction, not a loophole.

### Gaps
- No authoritative statement found confirming AI APIs work from a *sparse-packaged* (packaged with external location) WPF app specifically; it follows from "package identity" being the requirement but was not tested in any source.
- .NET 8 vs .NET 9: Windows AI APIs docs show .NET 8; Foundry Local's Windows quickstart says .NET 9 SDK "or later". Whether the Foundry Local WinML package supports net8.0 TFMs was not verified.

## KQ6. Quality, latency and limits of Phi Silica (params, context, languages, skills, moderation, structured output, tool calling, LoRA)

### Takeaway
Phi Silica is a ~3.3B-parameter, 4-bit (QuaRot+GPTQ) derivative of Phi-3.5-mini with a 4k token context, 8 supported languages at launch, ~230 ms TTFT and up to ~20 tok/s on Snapdragon X NPUs. The API offers free-form generation (streaming), Summarize / Rewrite (with tone) / Text-to-table / Conversation summary skills, **JSON-schema-constrained output** (`GenerateStructuredJsonResponseAsync`, stable since 2.3.1), embeddings, LoRA adapters (stable since 2.1.3; trained in Azure), and configurable content moderation. There is **no tool/function-calling API**; and since October 2026 generated text carries an invisible Unicode watermark that can break JSON/Markdown parsing.

### Cited Findings
- Size: Build 2024 coverage: "Phi Silica is the smallest model in the Phi family, with 3.3 billion parameters" — [VentureBeat](https://venturebeat.com/ai/microsoft-introduces-phi-silica-a-3-3b-parameter-model-made-for-copilot-pc-npus). Dec 2024 blog: "a Cyber-EO compliant derivative of Phi-3.5-mini"; context "2k tokens" at launch with "4k coming shortly" (model overview lists 4k); weights "4-bit, using QuaRot with GPTQ", activations 16-bit; "Up to 20 tokens per second"; "230 ms" time to first token for short prompts; context processing "4.8 mWh on the NPU (Snapdragon X Elite)"; token iteration "56% less power than on the CPU"; languages "English, Chinese (Simplified), French, German, Italian, Japanese, Portuguese, and Spanish" — [Phi Silica, small but mighty on-device SLM, 2024-12-06](https://blogs.windows.com/windowsexperience/2024/12/06/phi-silica-small-but-mighty-on-device-slm/). (Note: Dec 2024 figures are the only official numbers; Microsoft has not published updated throughput for 2025–26 component versions. The "650 tokens/s" from Build 2024 was a prompt-processing figure, not generation — [PCWorld](https://www.pcworld.com/article/2340495/microsoft-debuts-phi-silica-ai-specifically-for-copilot-pcs.html).)
- Current Microsoft description: "a Microsoft-developed, Transformer-based small language model that runs on the device's NPU ... supports text understanding, summarization, rewriting, and short-form generation" — [KB5124880](https://support.microsoft.com/help/5124880). NPU path uses "speculative decoding ... using a smaller draft model" — [Phi Silica](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica)
- Context limits acknowledged but not numerically stated in current docs: "The model has a fixed context window. Long prompts or multi-turn conversations may exceed this window"; language support "determined by its training data ... some languages may not be supported" — [Transparency Note](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica-transparency-note). API helpers: `GetUsablePromptLength(String)` "Returns the index in the given prompt where the context window reached the maximum number of supported tokens"; `LanguageModelContext` "Defines the tokens a language model can process at one time" — [LanguageModel class reference, updated 2026-09-30](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.ai.text.languagemodel)
- Language status codes added in 2.4.0: `LanguageModelResponseStatus.UnsupportedLanguage` and `LanguageMismatch` — [Windows App SDK 2.x release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable)
- Full `Microsoft.Windows.AI.Text` surface: `LanguageModel`, `LanguageModelContext`, `LanguageModelOptions`, `LanguageModelResponseResult`, `LanguageModelLowRankAdapter(+Result)`, `LanguageModelEmbeddingVectorResult`, `GenerateStructuredJsonResponseResult`, `TextRewriter`, `TextSummarizer`, `TextToTableConverter`, `TextToTableResponseResult`, `TextToTableRow`, `ConversationItem`, `ConversationSummaryOptions`; enums `GenerateStructuredJsonResponseStatus`, `InputKind`, `LanguageModelLowRankAdapterStatus`, `LanguageModelResponseStatus`, `TextRewriteTone` — [Microsoft.Windows.AI.Text namespace](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.ai.text)
- `LanguageModel` methods: `CreateAsync()`, `CreateContext()` / `CreateContext(String)` / `CreateContext(String, ContentFilterOptions)` (system-prompt context), `GenerateResponseAsync(String)` / `(String, LanguageModelOptions)` / `(LanguageModelContext, String, LanguageModelOptions)` — each "while returning progress for each token" (i.e. streaming via progress), `GenerateStructuredJsonResponseAsync(String, String[, LanguageModelOptions])` "constrained to a caller-supplied JSON schema", `GenerateEmbeddingVectors(String)`, `GenerateResponseFromEmbeddingsAsync(...)`, `GetUsablePromptLength`, `GetReadyState()`, `EnsureReadyAsync()`, properties `ModelName`, `ModelVersion` — [LanguageModel class](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.ai.text.languagemodel). Structured JSON API landed in stable 2.3.1 (2026-07-16) — [release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable)
- Text Intelligence skills: "Text-to-table ... Summarize ... Rewrite: Rephrases the prompt text to optimize clarity, readability, and, when specified, tone" — [Phi Silica](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica); watermark page also lists `TextRewriter.RewriteCustomAsync`, `TextSummarizer.SummarizeConversationAsync`, `SummarizeParagraphAsync` — [Watermarking in Windows AI text APIs](https://learn.microsoft.com/en-us/windows/ai/apis/text-watermarking)
- Content moderation: "Configurable content filtering across four categories (violence, hate, sexual content, self-harm) at multiple severity levels" via `ContentFilterOptions` / `PromptMaxAllowedSeverityLevel`; "Content moderation behavior is identical regardless of the inference hardware" — [Transparency Note](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica-transparency-note); code sample uses `Microsoft.Windows.AI.ContentSafety` — [Phi Silica](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica). LoRA API "promoted to stable" in 2.1.3 (2026-05-21) — [release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable). LoRA originally previewed at Build 2025 "on Snapdragon X Series NPUs", Intel/AMD "in the coming months" — [Build 2025 post](https://blogs.windows.com/windowsdeveloper/2025/05/19/advancing-windows-for-ai-development-new-platform-capabilities-and-tools-introduced-at-build-2025/)
- Intended uses per Microsoft: "In-app writing assistance ... Local Q&A ... Accessibility features: Simplifying complex text, generating descriptions, and supporting users who benefit from AI-assisted reading and writing ... Privacy-sensitive workflows"; cautions: "Do not use for high-stakes decision-making without human oversight"; "may be susceptible to prompt injection or jailbreak attempts" — [Transparency Note](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica-transparency-note)
- Quality parity NPU vs GPU: "output quality (accuracy, coherence, relevance) is consistent across Copilot+ and non-Copilot+ PCs because the same model weights and architecture are used" — [Transparency Note](https://learn.microsoft.com/en-us/windows/ai/apis/phi-silica-transparency-note)
- Semantic search / RAG: `AppContentIndex` APIs stable in 2.5.1 as a LAF; "semantic matching" only "on supported NPU-enabled devices" — [release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-2-0?pivots=stable) and [release channels](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-channels)

### Inferences
- Intent classification and structured output are well covered (JSON-schema API + text-to-table + Microsoft's own "intent detection" use-case language for Aion). Tool calling must be emulated by asking for JSON that names an action — exactly the `[ACTION:]`-line style already used elsewhere in OpenClicky — and then dispatching in app code; the JSON API is the right primitive because it is schema-constrained and (per the watermark list) not watermarked.
- Strip the four-code-point watermark before parsing any free-text output; do not rely on its position.
- 4k context and 8 languages mean long-document summarisation and non-Latin accessibility use should route to cloud per Microsoft's own guidance.

### Gaps
- No Microsoft-published latency/throughput for current (1.26xx) component versions, for Intel/AMD NPUs, or for the GPU path; only Dec 2024 Snapdragon numbers exist.
- Whether the 4k context has increased since Dec 2024 is not stated anywhere current.
- No official statement on whether `GenerateStructuredJsonResponseAsync` supports the full JSON Schema spec or a subset.
