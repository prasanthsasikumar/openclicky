## The eight decisions, as decided 2026-09-13

From the external review of 2026-09-11. Full context in
`docs/reviews/2026-09-11-external-review-triage.md`. All eight were put to Prasanth and answered;
this records the answers so they are not re-litigated. Four are done, three are parked behind a
product decision, one is still open work.

### Payments — parked, and not on Stripe's terms (decisions 1, 2, 3)

**Decided: park all payment work.** Not "fix Stripe later" — the payment rail itself is an open
question. India is the first market and **UPI is how India pays**; Stripe's subscription model is
not the shape that has to work first. Users outside India still have to be able to pay for the same
resources, so whatever replaces this is a two-rail decision, not a provider swap.

What that means for the three Stripe findings: they stay unfixed **and** the code stays dormant.
The unpinned API version, the `current_period_start` / `current_period_end` reads that Stripe moved
in its 2025 versions, the missing webhook idempotency table, the `null` `stripe_price_id` seeds for
`starter` and `pro`, and the read-then-spend credit race are all still exactly as the review
described them. None of them can bite while the product is invite-only and no Stripe route is
reachable, which is the condition that makes parking them safe.

Two things to carry into the payments decision whenever it happens:
- **The credit race is the one that blocks taking money**, whatever the rail. Credit checks are
  read-then-spend with no reservation, so parallel requests overspend. The fix is an atomic
  decrement in Postgres plus a migration — it is not Stripe-specific and it will be needed under
  UPI too.
- **Paid signup currently looks wired and is not.** If the Stripe path is going to sit dormant for
  a while, it is worth making it fail loudly rather than no-op, so nobody later mistakes "checkout
  returned" for "checkout worked".

### 4. Backend default — done: hosted is the default

**Decided: the online backend is the main one; local is for people who want to run their own.**
`agent/src/config.ts` already defaulted to the hosted backend and was already tested that way. The
three places that contradicted it — the `--backend-url` help text, `.env.example`, and CONTRIBUTING
— now say the same thing as the code, and frame `http://localhost:8787` as an override.

### 5. Linter and formatter — done: linters now, formatters still deferred

**Decided: go with the recommendation.** ESLint (with typescript-eslint, type-aware) and SwiftLint
are in, configured as linters only — no rule in either config rewrites whitespace, so the first run
did not touch every file and bury the history of the security pass. `swiftformat` / Prettier remain
deferred until after the dead-code pass, and both configs say so at the point where the formatting
rules are switched off.

Both gate CI on **errors only**. The backlog they expose is the point of having them:

| | Errors | Warnings | Command |
|---|---|---|---|
| ESLint | 0 | 371 | `npm run lint` |
| SwiftLint | 0 | 85 | `npm run lint:swift` (needs `brew install swiftlint`) |

The TypeScript warnings are almost entirely `any` reaching through untyped JSON; the Swift ones are
force unwraps and casts. Working either list down is a separate, mechanical pass.

The first run paid for itself: it found a **real concurrency bug** in the voice lane. `send_to_agent`
tool calls are dispatched from a fire-and-forget websocket handler, so two calls in one response
overlap — both read the same `threadId`, both run against it, and the later write wins, forking two
turns off one thread instead of continuing a conversation. Fixed by chaining the tasks.

### 7. Deploy target — done: no default, and no IP anywhere

**Decided: drop it, especially now that the domain exists.** `scripts/deploy-backend.sh` had
`SERVER="${OPENCLICKY_SERVER:-root@104.168.48.121}"`, so a public repo published both where the
server was and that it was reached as root — to every reader and every fork.

There is now **no default target**: `OPENCLICKY_SERVER` is required and the script exits 2 with
usage if it is unset. The public hostname is a second variable, `OPENCLICKY_API_HOST` (defaulting to
`api.openclicky.flowsxr.com`), and `backend/deploy/Caddyfile.openclicky` is now a template with
`__API_HOST__` substituted at deploy time — previously it hardcoded the hostname, so pointing the
script at another host would have written a site block for the wrong name.

```bash
export OPENCLICKY_SERVER=root@api.openclicky.flowsxr.com   # ssh target — the hostname, not the IP
scripts/deploy-backend.sh --env
```

The raw IP is gone from every tracked file except this one and the reference clones.

**On Porkbun:** the API credentials are on this machine, in
`~/Documents/GitHub/clearspace/.env.porkbun` (`PORKBUN_API_KEY` / `PORKBUN_SECRET_KEY`).

They do not help *here*, though: `wasd.tools` and `saathi.dev` are on Porkbun, but **`flowsxr.com`
is on NS1** (`dns1-4.p04.nsone.net`), so `api.openclicky.flowsxr.com` is not a Porkbun-managed
record and no Porkbun key can change it. Moving OpenClicky onto a Porkbun domain would change that;
`openclicky.com` is parked at Afternic and `openclicky.dev` / `.app` are at GoDaddy, none of them
ours today.

> **A search gotcha worth keeping.** `grep` on this Mac is **ugrep, and it honours `.gitignore` by
> default**. Since every credential file is gitignored (`.env*`), a content search sweeps straight
> past exactly the files that matter — `grep -ril porkbun .` in `clearspace/` returns nothing while
> `grep -ril --no-ignore-files porkbun .` finds it. "I grepped and found nothing" is not evidence of
> absence for secrets. Use `--no-ignore-files`, or find credential files by name (`find . -name
> '.env*'`) instead.

### 8. macOS structural work — the race is done; three pieces remain

**Decided: start here, to save resources.** The order was the CoreAudio race first because it
corrupts state at runtime while the others cost maintainability.

**Done — the render-thread race.** It was not a warning, it was a crash: under the Thread Sanitizer
the process aborts. `RealtimeAudioEngine.handleMicrophoneBuffer` read `converter`, `monoFormat` and
`onMicrophoneFrame` off `self` on the CoreAudio render thread while `tearDown()` nilled them on the
audio queue. `RealtimeAudioEngineConcurrencyTests` crashes on the old code and passes on the new.
The tap now copies one immutable snapshot from behind an unfair lock, and the class is `nonisolated`
so the project's `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` stops claiming state that lives off the
main actor (53 strict-concurrency warnings in that file down to 5).

`BuddyDictationManager` had the same bug **with no warning at all**, and that is the part worth
remembering: `AVAudioNodeTapBlock` is not `@Sendable`, so a tap closure inside a `@MainActor` class
is treated as main-actor isolated while in fact running on the render thread. Zero diagnostics, real
race. It read `activeTranscriptionSession` while the main actor reassigned and nilled it; it now
captures the session by value.

This is why AGENTS.md no longer says "do not attempt to fix the concurrency warnings". That note was
covering for two real races, and the more dangerous of the two never produced a warning to ignore.
139 strict-concurrency warnings remain across the app — a backlog to work a file at a time, with a
test each time, which is what caught these two.

**Still to do, in the recommended order:**
1. **~1,500 lines of dead code** — unused `DesignSystem` tokens while the HUD hardcodes 46 colour
   literals, `CompanionResponseOverlay.swift`, the onboarding video subsystem, Sparkle wired but
   commented out behind a Settings button that does nothing, half of `WindowPositionManager`, the
   `OpenClickyShell` target nothing builds, the boilerplate UI test target. Second in the order
   because it makes everything after it cheaper.
2. **`CompanionManager.swift`'s 1,689 lines across eight responsibilities**, plus the Accessibility
   helpers copy-pasted into four files with different nil semantics and eight backend requests each
   reimplementing URL building and auth.
3. **The Keychain migration.** `shell.json` is 0600 now, which was the cheap 90 %; moving to the
   Keychain is a real migration with a fallback path for existing installs.

## Windows, and what it means for everything above

**Decided: it has to work on both macOS and Windows.** Windows is the main market in India, which is
the first market — so Windows is not a port to consider later, it is a constraint on what gets built
from here.

Nothing in the decisions above conflicts with that, and one of them is now load-bearing for it: the
**hosted backend is the default**, which means a Windows client gets the same key-holding backend,
the same auth and the same metering with no second implementation. The provider-key boundary is the
piece of this project most worth keeping platform-independent.

What it does change: **SwiftLint is macOS-only, and so is the Swift app.** ESLint, the backend and
the agent CLI are already cross-platform and run on Windows unchanged. As Windows work starts, the
CI `macos-app` job stays where it is and anything new gets its own job — do not let a Windows client
inherit macOS-only tooling through the root scripts.

The research pass on existing Windows builds is in [WINDOWS-REFERENCE.md](WINDOWS-REFERENCE.md)
(cloned sources under `reference/windows/`, git-ignored). It was a separate thread and nothing in it
has been run — no Windows machine was involved.

# Saathi — the new project

Starting fresh in `~/Documents/GitHub/saathi`, pushed to the `saathihq` GitHub org. Domain
`saathi.dev` is registered.

**The idea, as stated:** a companion — approached from the accessibility side — that helps people
learn new things and play with them. Saathi is the companion; the accessibility framing is the way in,
not an afterthought bolted on.

**What carries over from OpenClicky, and what does not:** OpenClicky proved a few things worth
reusing — a Realtime voice session with native typed tools is fast enough to feel instant (~2 s versus
~12 s through an agent subprocess); typed tool arguments with closed enums keep a speech pipeline from
producing a wrong *command*; and the provider-key boundary (keys live in the backend, never reaching
the client or the agent) held up under external review. What should not carry over is the accumulated
structure: a 1,689-line central manager, four naming prefixes for one subsystem, and ~1,500 lines of
dead code are exactly what a fresh start exists to avoid.

**Open at the pause:** the product shape itself — who Saathi is for first, which accessibility need it
starts from, and what "learn and play" means concretely enough to build. That is a brainstorming
conversation, not a coding one, and it should happen before any architecture is chosen.
