## The eight open decisions

From the external review of 2026-09-11. Full context in
`docs/reviews/2026-09-11-external-review-triage.md`; this is the short form, in order of cost.

### 1. Stripe: which API version do you migrate to?
`backend/src/stripe.ts` pins no version, so Stripe serves the account default. The code reads
`sub.current_period_start` / `current_period_end`, which Stripe moved off the subscription object in
the 2025 versions — when the account default rolls forward those become `undefined`,
`new Date(undefined * 1000)` is `Invalid Date`, and subscription writes start failing. There is also
no webhook idempotency table, so a retried event is processed twice.
**Recommendation:** pin explicitly and fix the field reads to match. Largest live correctness risk.

### 2. Stripe prices: should paid signup work at all?
`backend/supabase/schema.sql:40-43` seeds `starter` and `pro` with `stripe_price_id = null`, so
checkout for both is a no-op in production; tests pass on the in-memory store's fake prices. (`free`
needs no price; `invite`'s null is deliberate and documented.)
**Recommendation:** if invite-only is the model, make the paid path fail loudly rather than look wired.

### 3. Launch paid before fixing the credit race?
Credit checks are read-then-spend with no reservation, so parallel requests overspend. The real fix
is an atomic decrement in Postgres plus a migration, not application-side locking.
**Recommendation:** fine while invite-only; blocking before taking money.

### 4. Backend default: hosted or localhost?
`agent/src/config.ts:88` defaults to `https://api.openclicky.flowsxr.com`. `cli.ts:64` help says
"default http://localhost:8787". `.env.example:70` says the opposite of the help. Three places disagree.
**Recommendation:** keep hosted, correct the help text and docs.

### 5. Linter and formatter: which, and when to take the churn?
Nothing exists — no ESLint, Prettier, SwiftLint, SwiftFormat, `.editorconfig`. A formatter's first run
rewrites every file and buries recent history.
**Recommendation:** ESLint + SwiftLint now; formatters after the dead-code pass.

### 6. Repo clutter: what else goes?
`PROMPT-initial-cut.md` and `REVERSE-ENGINEERING.md` were deleted on 2026-09-13 (they are in git
history if ever needed). Eight documents still describe the Mac app; consolidating them is editorial.

### 7. Deploy target: default or required?
`scripts/deploy-backend.sh:12` is `SERVER="${OPENCLICKY_SERVER:-root@104.168.48.121}"` — overridable,
but a public repo carries the server IP and root login as its default.
**Recommendation:** require `OPENCLICKY_SERVER`, drop the baked-in default.

### 8. The macOS structural work: which first?
Four separate reviewable changes: ~1,500 lines of dead code; the Keychain migration (`shell.json` is
now 0600, which is the cheap 90 %); main-actor state mutated from the CoreAudio render thread — a real
data race that the project's "ignore the concurrency warnings" note hides; and splitting
`CompanionManager`'s 1,689 lines.
**Recommendation:** the CoreAudio race first (it corrupts state at runtime, the others cost
maintainability), dead code second because it makes everything after it cheaper.

# Saathi — the new project

Starting fresh in `~/Documents/GitHub/saathi`, pushed to the `saathihq` GitHub org. Domain
`saathi.dev` is registered.

**The idea, as stated:** a companion — approached from the accessibility side — that helps people
learn new things and play with them. Saathi is the companion; the accessibility framing is the way in,
not an afterthought bolted on.

**What carries over from OpenClicky, and what does not:** OpenClicky proved a few things worth
reusing — a Realtime voice session with native typed tools is fast enough to feel instant (~2 s versus
~12 s through an agent subprocess); typed tool arguments with closed enums keep a speech pipeline from
producing a wrong *command*; and the provider-key boundary (keys live in the backend, never reaching
the client or the agent) held up under external review. What should not carry over is the accumulated
structure: a 1,689-line central manager, four naming prefixes for one subsystem, and ~1,500 lines of
dead code are exactly what a fresh start exists to avoid.

**Open at the pause:** the product shape itself — who Saathi is for first, which accessibility need it
starts from, and what "learn and play" means concretely enough to build. That is a brainstorming
conversation, not a coding one, and it should happen before any architecture is chosen.
